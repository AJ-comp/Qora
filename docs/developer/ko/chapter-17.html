CFG의 successor와 predecessor

Terminator의 이동 정보를 두 방향의 그래프로 읽는 과정

← 이전: MIR snapshot전체 목차
다음 주제: 도달 가능성과 지배 관계 →

CFG는 block 사이의 이동 관계를 나타내는 그래프입니다.
Qora는 새로운 실행 구조를 다시 만드는 대신, 이미 각 block 끝에 놓인 Terminator를 읽어 이 그래프를 계산합니다.

CFG를 만들 Qora 코드

function Next(value: int): int
{
    return value + 1;
}

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

14장에서 이 조건문은 네 block으로 나뉘었습니다.
b0은 조건을 판단하고, b1은 참 본문을 실행하며, b2는 거짓 경로를 나타냅니다. 마지막 b3에서는 두 경로가 합쳐진 뒤 H를 실행합니다. 

        ┌──→ b1: X ──┐
b0: 조건              ├──→ b3: H → return
        └──→ b2 ─────┘

화살표의 원본은 Terminator입니다

모든 block은 마지막에 하나의 Terminator를 가집니다.
일반 MIR 명령이 값을 계산하거나 게이트를 적용한다면, Terminator는 이 block이 끝난 뒤 어디로 이동할지를 정합니다. 

b0.Terminator = Branch
├─ 조건이 참  → b1
└─ 조건이 거짓 → b2

b1.Terminator = Jump → b3
b2.Terminator = Jump → b3
b3.Terminator = Return

Branch는 목적지가 두 개이고, Jump는 목적지가 하나입니다.
Return은 callable 실행을 끝내므로 다음 block이 없습니다. CFG는 바로 이 사실을 표로 정리한 결과입니다.

다음 block을 모으면 successor 표가 됩니다

successor는 “현재 block 다음에 갈 수 있는 block”입니다.
분석기는 각 block의 Terminator가 가리키는 목적지를 읽어 다음 표를 만듭니다. 

Successors
├─ b0 → [b1, b2]
├─ b1 → [b3]
├─ b2 → [b3]
└─ b3 → []

b0에서는 조건에 따라 두 곳 중 하나로 갈 수 있으므로 successor가 두 개입니다.
b1과 b2는 모두 합류 block b3으로 이동하고, b3은 반환하므로 빈 목록을 가집니다.

주의 successor가 두 개라고 해서 두 block을 모두 실행한다는 뜻은 아닙니다.
CFG는 실행 중 선택될 수 있는 경로 전체를 나타내며, 실제 실행에서는 조건에 맞는 한 경로만 선택됩니다.

화살표를 뒤집으면 predecessor 표가 됩니다

predecessor는 “현재 block으로 들어올 수 있는 이전 block”입니다.
별도의 소스에서 다시 계산하지 않고, 완성된 successor 화살표의 방향만 뒤집습니다. 

Successor 화살표                 뒤집은 Predecessor 관계
b0 → b1                          b1 ← b0
b0 → b2                          b2 ← b0
b1 → b3                          b3 ← b1
b2 → b3                          b3 ← b2

Predecessors
├─ b0 ← []
├─ b1 ← [b0]
├─ b2 ← [b0]
└─ b3 ← [b1, b2]

진입 block b0으로 들어오는 block은 없으므로 빈 목록입니다.
합류 block b3에는 참 경로 b1과 거짓 경로 b2가 모두 들어오므로 predecessor가 두 개입니다.

predecessor를 successor에서 만들면 두 표의 기준이 하나로 유지됩니다.
한쪽에서는 b1 → b3인데 다른 쪽에서는 b3 ← b1이 빠지는 식의 불일치를 피할 수 있습니다.

두 표가 callable의 CFG snapshot이 됩니다

현재 snapshot에서 Work의 CFG를 요청하면 분석 저장소가 Work의 block과 Terminator를 읽습니다.
그 결과 successor와 predecessor를 포함한 MirControlFlowSnapshot이 만들어집니다. 

MirSnapshot
└─ Work의 CFG
   └─ MirControlFlowSnapshot
      ├─ SourceCallable = Work
      ├─ EntryBlock = b0
      ├─ SuccessorsOf(b0) = [b1, b2]
      └─ PredecessorsOf(b3) = [b1, b2]

이 CFG snapshot은 실행할 두 번째 block 트리가 아닙니다.
원래 Work의 block을 그대로 가리키면서, 그 관계를 빠르게 질문할 수 있도록 정리한 파생 정보입니다.

정리 Terminator가 block 이동의 원본이고, successor는 그 이동을 정방향으로 정리한 표입니다.
predecessor는 같은 화살표를 뒤집은 표이며, 두 결과는 하나의 callable 전용 CFG snapshot으로 묶여 이후 MIR 분석의 기반이 됩니다.
