MirProgram, MirSnapshot, 분석 저장소

완성된 Next와 Work가 검증된 최초 MIR snapshot으로 발행되는 실제 호출 순서

← 이전: 조건문 lowering전체 목차
다음: CFG 간선 →

15장 끝에서 Work c44의 마지막 instruction과 Terminator까지 모두 완성되었습니다.
이제 그 결과가 들어 있는 실제 지역 변수 mirCallables와 mirEntryCallable에서 출발하여, MirProgram 생성, 검증, MirSnapshot 발행, 첫 CFG 요청까지를 하나의 호출 흐름으로 연결합니다.

이번 장의 입력을 만든 소스

function Next(value: int): int
{
    return value + 1;
}

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

앞 장들에서 Next h6은 Next c6으로, Work h44는 Work c44로 내려왔습니다.
이제 소스 문장을 다시 lowering하지 않습니다. 완성된 두 MirCallable 객체를 하나의 발행 가능한 결과로 묶는 단계입니다.

callable 순회가 끝난 실제 지역 변수

LowerHirArtifact의 foreach가 두 번 실행된 직후 상태는 다음과 같습니다.
mirEntryCallable은 ID를 다시 검색한 결과가 아니라, 두 번째 반복에서 hirCallable과 HIR 진입점이 같은 객체였기 때문에 방금 생성된 Work c44 객체를 그대로 받은 값입니다. 

// foreach 종료 직후의 예제값
hirProgram.Callables   = [Next h6, Work h44]
hirEntryCallable       = Work h44

mirCallables           = [Next c6, Work c44]
mirEntryCallable       = Work c44

ReferenceEquals(mirCallables[1], mirEntryCallable) = true

이 두 지역 변수는 LowerHirArtifact의 callable 순회에서 만들어졌습니다.
다음 전체 함수에 공통 예제의 값을 대입하면 생성 위치와 이후 소비 순서를 함께 확인할 수 있습니다. 

private static MirSnapshot LowerHirArtifact(
    HirSemanticArtifact hirArtifact,
    IMirLoweringTraceSink? traceSink)
{
    ArgumentNullException.ThrowIfNull(hirArtifact);

    var hirSnapshot = hirArtifact.Source;
    var hirProgram = hirSnapshot.Program;
    // 예제값: Callables=[Next h6, Work h44], EntryCallable=Work h44

    var hirEntryCallable = hirProgram.EntryCallable
        ?? throw new InvalidOperationException(
            "validated HIR must contain an operation before MIR lowering");

    var mirCallables = new List<MirCallable>();
    MirCallable? mirEntryCallable = null;

    foreach (var hirCallable in hirProgram.Callables)
    {
        // 1회차 hirCallable=Next h6, 2회차=Work h44
        var mirCallableLowerer = new HirCallableToMirLowerer(
            hirCallable,
            hirArtifact,
            traceSink);
        var mirCallable = mirCallableLowerer.LowerToMirCallable();
        // 1회차 결과=Next c6, 2회차 결과=Work c44

        mirCallables.Add(mirCallable);
        if (ReferenceEquals(hirCallable, hirEntryCallable))
            mirEntryCallable = mirCallable;
        // 2회차에서만 true: mirEntryCallable=Work c44
    }

    var mirProgram = new MirProgram(
        mirEntryCallable
            ?? throw new InvalidOperationException(
                "validated HIR entry callable must be lowered into MIR"),
        mirCallables);
    // 실제 인수: entryPoint=Work c44,
    // callables=[Next c6, Work c44]

    return MirSnapshot.CreateLowered(mirProgram);
}

MirProgram 생성자 안에서 확정되는 소유 관계

위 함수의 다음 진입점은 new MirProgram(Work c44, [Next c6, Work c44])입니다.
생성자는 먼저 목록과 ID index를 만든 뒤, 전달된 진입점이 그 목록 안의 정확한 객체인지 확인합니다. 

internal MirProgram(
    MirCallable entryPoint,                 // Work c44
    IEnumerable<MirCallable> callables)     // [Next c6, Work c44]
{
    ArgumentNullException.ThrowIfNull(entryPoint);
    ArgumentNullException.ThrowIfNull(callables);

    Callables = MirCollections.Freeze(callables);
    // [Next c6, Work c44]
    _callables = IndexCallables(Callables);
    // { c6 → Next 객체, c44 → Work 객체 }

    if (!_callables.TryGetValue(entryPoint.Id, out var ownedEntryPoint)
        || !ReferenceEquals(ownedEntryPoint, entryPoint))
    {
        throw new ArgumentException(
            $"entry callable {entryPoint.Id} must be the exact object owned by this MIR program",
            nameof(entryPoint));
    }
    // ownedEntryPoint=목록의 Work c44, entryPoint=같은 Work c44 → 통과

    if (entryPoint.Kind != MirCallableKind.Operation)
    {
        throw new ArgumentException(
            "the MIR entry callable must be an operation",
            nameof(entryPoint));
    }
    // Work.Kind=Operation → 통과

    if (entryPoint.Parameters.Count != 0)
    {
        throw new ArgumentException(
            "the MIR entry callable must not declare parameters",
            nameof(entryPoint));
    }
    // Work.Parameters=[] → 통과

    HirArtifact = RequireSingleHirArtifact(entryPoint, Callables);
    EnsureExclusiveEntityOwnership(Callables);
    EntryPoint = entryPoint;
}

IndexCallables는 c6과 c44를 key로 등록하며, 중복 callable ID가 있으면 생성 중에 거부합니다.
이어서 RequireSingleHirArtifact가 두 callable뿐 아니라 그 아래의 value, storage, qubit, block, Terminator, instruction, qubit access의 Origin까지 순회합니다. 공통 예제의 모든 origin은 동일한 최종 HIR artifact를 가리키므로 검사를 통과합니다. 

// RequireSingleHirArtifact의 이번 결과
hirArtifact = Work c44의 Origin이 가리키는 최종 effect-analysis artifact

Next c6의 모든 entity.Origin.SourceHirOrigin.HirArtifact
    ReferenceEquals hirArtifact → true
Work c44의 모든 entity.Origin.SourceHirOrigin.HirArtifact
    ReferenceEquals hirArtifact → true

MirProgram.HirArtifact = hirArtifact

그다음 EnsureExclusiveEntityOwnership은 reference equality를 사용하는 작업용 dictionary에 각 객체와 소유 callable ID를 등록합니다.
예를 들어 Work c44의 b0, %v10, q0.v2, i15는 모두 owner c44로 등록됩니다. 같은 객체가 Next c6 아래에도 나타나면 즉시 예외가 발생하지만, 공통 예제에는 그런 공유가 없습니다. 

// EnsureExclusiveEntityOwnership의 예제 등록 일부
owners[Next의 %v0 객체] = c6
owners[Next의 b0 객체]  = c6

owners[Work의 b0 객체]  = c44
owners[Work의 %v10 객체]= c44
owners[Work의 i15 객체] = c44
owners[Work의 q0.v2 객체] = c44

// 충돌 없음 → EntryPoint=Work c44 대입까지 완료

CreateLowered가 여는 최초 snapshot 생성자

MirProgram 생성이 끝나면 제어가 LowerHirArtifact의 마지막 줄로 돌아옵니다.
지역 변수 mirProgram은 방금 검사를 통과한 동일한 객체이며, CreateLowered는 이 객체를 private root 생성자에 그대로 전달합니다. 

// LowerHirArtifact의 마지막 줄
return MirSnapshot.CreateLowered(mirProgram);

// 실제 구현 전체
internal static MirSnapshot CreateLowered(MirProgram program) =>
    new(program);
// 예제 인수
program.EntryPoint = Work c44
program.Callables  = [Next c6, Work c44]

root 생성자의 첫 분기: HIR 준비 상태

private 생성자는 먼저 program.HirArtifact를 지역 변수로 꺼냅니다.
이 값은 앞의 RequireSingleHirArtifact가 확정한 바로 그 artifact이며, 같은 객체가 MIR 생성자의 HIR 근거로 이어집니다. 

private MirSnapshot(MirProgram program)
{
    ArgumentNullException.ThrowIfNull(program);

    var hirArtifact = program.HirArtifact;
    // 예제값: 최종 effect-analysis artifact

    if (!hirArtifact.IsReadyForMirLowering)
    {
        throw new ArgumentException(
            "MIR lowering requires a HIR artifact ready for MIR lowering.",
            nameof(program));
    }
    QoraMirVerifier.VerifyOrThrow(program);

    Stage = MirStage.Lowered;
    Program = program;
    HirArtifact = hirArtifact;
    PreviousSnapshot = null;
    Analyses = new MirAnalysisStore(program);
}

IsReadyForMirLowering은 새 분석을 실행하지 않고 이미 기록된 두 값을 확인하는 계산 property입니다.
공통 예제의 artifact는 effect analysis 단계이고 validation이 승인되었으므로 조건은 참입니다. 

public bool IsReadyForMirLowering =>
    Phase == HirSemanticPhase.EffectAnalysis && IsAccepted;
// 예제값
Phase      = EffectAnalysis
IsAccepted = true
IsReadyForMirLowering = true

!true → false  // 예외 분기를 건너뜀

VerifyOrThrow의 실제 호출 사슬

준비 상태를 통과한 다음 줄은 QoraMirVerifier.VerifyOrThrow(program)입니다.
이 호출은 Verify → new Verifier(program).Run → VerifyCallable로 이어집니다. 

public static void VerifyOrThrow(MirProgram program)
{
    var errors = Verify(program);
    if (errors.Count == 0) return;

    var message = new StringBuilder("QINTERNAL: invalid Qora MIR");
    foreach (var error in errors)
        message.AppendLine().Append("  ").Append(error);
    throw new InvalidOperationException(message.ToString());
}

public static IReadOnlyList<MirVerificationError> Verify(MirProgram program)
{
    ArgumentNullException.ThrowIfNull(program);
    return new Verifier(program).Run();
}

Run은 ID 순서로 Next c6을 먼저, Work c44를 다음에 검사합니다.
각 callable에서는 CFG를 임시로 계산하여 큐비트 흐름, block 내용, 그래프 계약을 확인합니다. 여기서 AnalyzeUnchecked의 “unchecked”는 callable 생성자가 동일 callable 밖의 CFG target을 이미 거부했으므로 verifier를 재귀 호출하지 않는다는 뜻입니다. 

public IReadOnlyList<MirVerificationError> Run()
{
    foreach (var callable in
             _program.Callables.OrderBy(callable => callable.Id.Value))
        VerifyCallable(callable);
    // 반복값: Next c6 → Work c44

    if (_errors.Count == 0)
        VerifyQubitWriteContracts();

    return _errors;
}

private void VerifyCallable(MirCallable callable)
{
    var callableErrorStart = _errors.Count;
    VerifyQubitSeeds(callable);

    var controlFlow = MirControlFlowAnalysis.AnalyzeUnchecked(callable);
    VerifyQubitFlow(callable, controlFlow);
    VerifyBlockContents(callable, controlFlow);

    if (_errors.Count == callableErrorStart)
        VerifyGraphContracts(callable, controlFlow);
}

Work c44 차례에는 15장에서 만든 b0 → [b1,b2], b1 → b3, b2 → b3, b3 → []이 분석됩니다.
이 CFG를 이용하여 %v10이 b0의 branch 전에 정의되었는지, q0.v2의 두 Phi 입력이 실제 b3 incoming edge와 맞는지, H가 q0.v2 이후의 버전 q0.v3을 만드는지 확인합니다. 오류가 없으므로 VerifyOrThrow는 예외 없이 반환합니다.

검증 뒤에 대입되는 MirSnapshot 필드

verifier가 반환한 뒤에야 root 생성자의 다섯 대입이 실행됩니다.
Program은 복사본이 아니라 생성자에 들어온 동일한 mirProgram 객체이며, 최초 snapshot이므로 이전 snapshot은 없습니다. 

Stage = MirStage.Lowered;
// Lowered

Program = program;
// EntryPoint=Work c44, Callables=[Next c6, Work c44]

HirArtifact = hirArtifact;
// 위 두 callable의 모든 Origin이 공유하는 exact artifact

PreviousSnapshot = null;
// 최초 snapshot

Analyses = new MirAnalysisStore(program);
// 이 program만 받는 새 분석 저장소

따라서 MirSnapshot은 MIR을 한 벌 더 복사한 객체가 아닙니다.
검증을 통과한 정확한 MirProgram, 현재 stage, 원본 HIR artifact, 이 program 전용 분석 진입점을 함께 발행하는 단위입니다.

MirAnalysisStore 생성 직후의 상태

마지막 대입이 호출하는 생성자의 인수도 동일한 program입니다.
생성자는 program-wide 분석인 call graph와 effects의 Lazy factory를 준비하지만, callable별 CFG dictionary는 아직 비어 있습니다. 

internal MirAnalysisStore(MirProgram program)
{
    _program = program
        ?? throw new ArgumentNullException(nameof(program));
    _callGraph = NewLazy(
        () => MirCallGraphAnalysis.AnalyzeVerified(_program));
    _effects = NewLazy(
        () => MirEffectAnalysis.AnalyzeVerified(
            CallGraph,
            callable => StorageProvenance(callable),
            callable => PathConditions(callable)));
}
// 생성 직후 예제 상태
_program.EntryPoint = Work c44
_controlFlow        = {}
_callGraph.IsValueCreated = false
_effects.IsValueCreated   = false

즉 snapshot 발행만으로 CFG, call graph, effects가 모두 계산되지는 않습니다.
저장소는 요청받은 분석만 계산하고, 그 결과를 이 snapshot의 수명 동안 재사용합니다.

기본 컴파일 경로의 실제 첫 소비 코드

기본 CLI 경로는 root snapshot을 받은 직후 임의로 Work의 CFG부터 요청하지 않습니다.
QoraCompiler의 실제 다음 두 문장은 ToMir이 반환한 snapshot을 지역 변수 mir에 저장하고, 곧바로 그 snapshot의 전체 effect 분석을 강제로 평가합니다. 

mir = builtHir.ToMir(
    instrumentation?.MirLowering);
// 예제값: mir.Program.Callables=[Next c6, Work c44]
//         mir.Analyses._controlFlow={}

_ = mir.Analyses.Effects;
// 실제 첫 분석 요청

공개 property Effects는 생성 시 준비한 _effects의 Value를 읽습니다.
따라서 이 줄에서 effect factory가 처음 실행되며, 생성자에서 연결해 둔 CallGraph, StorageProvenance, PathConditions가 실제 호출로 바뀝니다. 

public MirEffectSnapshot Effects => _effects.Value;

// _effects가 실행하는 factory
MirEffectAnalysis.AnalyzeVerified(
    CallGraph,
    callable => StorageProvenance(callable),
    callable => PathConditions(callable))

Effects에서 call graph와 callable 순회로

AnalyzeVerified 호출 인수를 평가할 때 먼저 CallGraph property가 _callGraph.Value를 읽습니다.
MirCallGraphAnalysis.AnalyzeVerified(_program)이 Next c6과 Work c44의 instruction을 순회한 결과, 공통 예제에서는 Work c44/i6 → Next c6 호출 하나가 기록됩니다. 

public MirCallGraph CallGraph => _callGraph.Value;
// 첫 평가 결과
MirCallGraph.Calls
└─ MirCallSite
   ├─ Instruction = c44/i6
   ├─ Caller      = c44
   └─ Callee      = c6

완성된 call graph와 두 provider delegate가 MirEffectAnalysis.AnalyzeVerified에 전달됩니다.
이 메서드는 Analyzer.Run을 호출하고, Run은 formal qubit summary를 준비한 다음 _program.Callables의 저장 순서 그대로 반복합니다. 따라서 첫 callable은 Next c6이고 두 번째가 Work c44입니다. 

public MirEffectSnapshot Run()
{
    var orderedSummaries = _qubitEffects.SummarizeAll();

    var effects = new List<MirQuantumInstructionEffect>();
    foreach (var callable in _program.Callables)
    {
        // 1회차 callable=Next c6
        // 2회차 callable=Work c44
        var storage = _storageProvenance(callable);
        storage.EnsureFor(callable);
        var paths = _pathConditions(callable);
        paths.EnsureFor(callable);
        foreach (var block in callable.Blocks)
        {
            foreach (var instruction in block.Instructions)
            {
                switch (instruction)
                {
                    case MirQuantumApply apply:
                        effects.Add(DescribeApply(
                            callable,
                            apply,
                            storage,
                            paths));
                        break;
                    case MirMeasure measure:
                        effects.Add(DescribeMeasure(
                            callable,
                            measure,
                            paths));
                        break;
                }
            }
        }
    }

    return new MirEffectSnapshot(_program, effects, orderedSummaries);
}

Next c6 처리로 먼저 채워지는 cache

첫 반복에서 StorageProvenance(Next c6)가 _storageProvenance[c6]을 계산합니다.
이어지는 PathConditions(Next c6)의 factory는 내부에서 ControlFlow(Next c6)을 요청하므로, 비어 있던 CFG cache에는 c6이 먼저 들어갑니다. 

public MirStorageProvenanceSnapshot StorageProvenance(
    MirCallable callable)
{
    var source = _program.RequireCallable(callable);
    return _storageProvenance.GetOrAdd(
        source.Id,
        _ => NewLazy(
            () => MirStorageProvenanceAnalysis.AnalyzeUnchecked(source))).Value;
}

public MirPathConditionSnapshot PathConditions(MirCallable callable)
{
    var source = _program.RequireCallable(callable);
    return _pathConditions.GetOrAdd(
        source.Id,
        _ => NewLazy(
            () => MirPathConditionAnalysis.AnalyzeVerified(
                ControlFlow(source)))).Value;
}
// Next 반복의 실제 호출
StorageProvenance(Next c6)
→ PathConditions(Next c6)
  → ControlFlow(Next c6)
    → AnalyzeUnchecked(Next c6)

// Next 반복 종료 직후
_storageProvenance.Keys = [c6]
_pathConditions.Keys    = [c6]
_controlFlow.Keys       = [c6]

Next c6에는 quantum instruction이 없으므로 instruction 반복은 effect를 추가하지 않습니다.
그러나 PathConditions를 준비하는 과정에서 CFG는 이미 계산되었으며, 이 결과는 같은 store의 key c6에 남습니다.

두 번째 반복이 시작되면 callable=Work c44입니다.
이 시점에는 c6 CFG만 cache되어 있고 c44 key는 아직 없습니다. 먼저 StorageProvenance(Work c44)가 배열 values의 provenance를 계산한 뒤, PathConditions(Work c44)이 처음으로 ControlFlow(Work c44)을 요청합니다. 

// Work 반복 시작 직전
_controlFlow =
{
    c6 → Lazy(completed Next CFG)
}

callable = Work c44
StorageProvenance(Work c44)
→ PathConditions(Work c44)
  → ControlFlow(Work c44)

// ControlFlow 진입 직전에도 c44 key는 없음
_controlFlow.ContainsKey(c44) = false

verifier의 CFG가 cache에 남지 않는 이유

verifier도 앞서 AnalyzeUnchecked(Next c6)과 AnalyzeUnchecked(Work c44)을 호출했지만, Effects의 의존성 계산은 두 CFG를 다시 계산합니다.
verifier가 실행될 때는 root 생성자의 Analyses = new MirAnalysisStore(program) 대입 전이므로 store 자체가 아직 존재하지 않습니다. verifier의 지역 변수 controlFlow는 검사가 끝나면 사라지고, 발행된 snapshot의 cache에는 들어가지 않습니다. 

MirSnapshot root 생성자
├─ HIR readiness 확인
├─ VerifyOrThrow(program)
│  ├─ AnalyzeUnchecked(Next c6)    // 검증용 지역 결과
│  └─ AnalyzeUnchecked(Work c44)   // 검증용 지역 결과
├─ Stage/Program/HirArtifact 대입
└─ new MirAnalysisStore(program)   // 빈 cache 생성

QoraCompiler의 실제 다음 요청: Effects
├─ Next 반복의 PathConditions
│  └─ ControlFlow(Next c6)         // cache에 c6 추가
└─ Work 반복의 PathConditions
   └─ ControlFlow(Work c44)        // cache에 c44가 없으므로 최초 분석
      └─ AnalyzeUnchecked(Work c44)

17장은 마지막 ControlFlow(Work c44) 내부에서 source=Work c44가 확정되고 GetOrAdd가 c44용 Lazy를 추가하는 순간부터 이어집니다.
그 분석이 반환된 뒤에는 PathConditions(Work)과 effect instruction 순회가 계속되며, 같은 lowered snapshot을 사용하는 후속 CFG 요청은 cache hit가 됩니다.
