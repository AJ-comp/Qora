Callable lowering 구현 함수 따라가기

이전 장에서 준비한 callable 전용 lowerer가 실제 MirCallable을 만드는 C# 호출 경로

LowerHirArtifact()

선택한 세부 흐름

최종 HIR artifact가 MIR lowering으로 들어오는 첫 함수 LowerHirArtifact()의 세부 흐름입니다.

LowerHirArtifact(...)

최종 HIR의 callable을 하나씩 MIR로 바꾸고, 결과를 최초 MirSnapshot으로 묶는 함수입니다.
이번 추적에서는 foreach가 Next와 Work를 차례로 처리합니다.

먼저 전체 함수를 확인합니다

아래 코드는 세부 흐름을 확인할 LowerHirArtifact() 전체입니다.
먼저 HIR 프로그램을 읽고 두 callable을 변환한 뒤 MirSnapshot을 반환하는 순서를 확인합니다.
테두리와 세부 흐름 보기 뱃지가 있는 호출부를 선택하면 LowerToMirCallable()의 실행 흐름으로 이동합니다. 

private static MirSnapshot LowerHirArtifact(
    HirSemanticArtifact hirArtifact,
    IMirLoweringTraceSink? traceSink)
{
    ArgumentNullException.ThrowIfNull(hirArtifact);

    var hirSnapshot = hirArtifact.Source;
    var hirProgram = hirSnapshot.Program;

    var hirEntryCallable = hirProgram.EntryCallable
        ?? throw new InvalidOperationException(
            "validated HIR must contain an operation before MIR lowering");

    var mirCallables = new List<MirCallable>();
    MirCallable? mirEntryCallable = null;

    foreach (var hirCallable in hirProgram.Callables)
    {
        var mirCallableLowerer = new HirCallableToMirLowerer(
            hirCallable,
            hirArtifact,
            traceSink);

        var mirCallable = mirCallableLowerer.LowerToMirCallable();
        mirCallables.Add(mirCallable);

        if (ReferenceEquals(hirCallable, hirEntryCallable))
            mirEntryCallable = mirCallable;
    }

    var mirProgram = new MirProgram(
        mirEntryCallable
            ?? throw new InvalidOperationException(
                "validated HIR entry callable must be lowered into MIR"),
        mirCallables);

    return MirSnapshot.CreateLowered(mirProgram);
}

이제 이 함수에 전달되는 Qora 프로그램을 놓고 각 코드 범위의 실행 결과를 순서대로 따라갑니다.

LowerHirArtifact()가 처음 받는 프로그램

function Next(value: int): int
{
    return value + 1;
}

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

이 함수는 아직 배열 선언이나 if 같은 개별 문장을 직접 처리하지 않습니다.
먼저 프로그램에서 두 선언을 꺼내 Next h6과 Work h44라는 두 callable로 봅니다. Work 안의 Next(values[0])은 새로운 세 번째 callable이 아니라, 이미 목록에 있는 Next h6을 호출하는 표현식입니다.
또한 실행을 시작할 수 있는 operation은 Work이므로 EntryCallable도 Work h44입니다.

foreach 실행 전·후 구조 비교

반복문이 시작되기 전에는 변환된 callable 목록이 비어 있고, MIR 진입 callable도 정해지지 않았습니다.
두 번의 반복이 끝나면 Next c6과 Work c44이 목록에 들어가며, mirEntryCallable은 그 목록의 Work c44 객체를 가리킵니다.

두 callable 변환↓

반환되는 MirSnapshot 구조

이번 장에서 살펴본 LowerHirArtifact()는 HIR 프로그램의 callable을 차례로 MIR callable로 변환하고, 그 결과를 MirSnapshot으로 묶어 반환합니다.

Qora 예제에서는 Next h6과 Work h44가 MirCallable Next c6과 MirCallable Work c44로 변환되고, Work c44가 진입점으로 선택되는 흐름을 확인했습니다.

아래 전체 코드에서 LowerToMirCallable() 호출부를 선택하면 HIR callable 하나가 MirCallable로 변환되는 세부 흐름을 다시 확인할 수 있습니다.

LowerToMirCallable()

선택한 세부 흐름

HIR callable 하나를 MirCallable로 완성하는 흐름입니다.

LowerHirArtifact()→mirCallableLowerer.LowerToMirCallable()

하나의 HIR callable을 진입 block, 매개변수, 본문, 종료를 가진 MirCallable로 완성하는 중심 함수입니다.
공통 예제에서는 Next h6을 가진 lowerer와 Work h44을 가진 lowerer에서 각각 한 번씩 실행됩니다.

먼저 전체 함수를 확인합니다

아래 코드는 세부 흐름을 확인할 LowerToMirCallable() 전체입니다.
먼저 함수가 어떤 순서로 callable을 준비하고 반환하는지 확인한 뒤, Next h6과 Work h44을 각각 대입하여 각 코드 범위가 만드는 상태를 살펴봅니다.
테두리와 세부 흐름 보기 뱃지가 있는 코드 영역을 선택하면 해당 함수의 실행 흐름으로 이동합니다. 

public MirCallable LowerToMirCallable()
{
    var mirCallableOrigin = MirOriginFor(_hirCallable);
    var hirCallableSymbol = RequireHirDeclarationSymbol(
        _hirCallable.Id,
        $"callable `{_hirCallable.Name}`");
    var hirScopeGraph = _hirArtifact.Model.ScopeGraph
        ?? throw MirLoweringError(
            "the final HIR semantic model has no scope graph");
    var qualifiedSourceCallableName =
        hirScopeGraph.QualifiedName(hirCallableSymbol);

    _currentMirBlockBuilder = CreateMirBlock(mirCallableOrigin);

    LowerParameters();
    LowerStatements(_hirCallable.Body.Statements);

    CloseCallableBody(mirCallableOrigin);

    var mirBlocks = BuildMirBlocks();

    return new MirCallable(
        _mirCallableId,
        qualifiedSourceCallableName,
        _hirCallable.ReturnType is { } returns
            ? MirType.Scalar(returns)
            : null,
        _mirParameters,
        mirBlocks,
        mirCallableOrigin);
}

이제 첫 번째 실행인 Next h6을 대입하여, 위 코드가 매개변수와 본문을 어떤 MIR 상태로 바꾸는지 순서대로 따라갑니다.

Next 함수가 MirCallable로 완성되는 과정

function Next(value: int): int
{
    return value + 1;
}

먼저 Next 원본 코드의 각 요소가 매개변수와 본문 lowering에서 어떤 MIR 결과를 만드는지 확인합니다.
이 실행의 시작값은 _hirCallable = Next h6, _mirCallableId = c6입니다.

Next 실행 전·후 구조 비교

호출 직전에는 builder와 MIR 매개변수 목록이 비어 있고, 현재 block도 아직 없습니다.
반환 직전에는 b0와 value 매개변수가 등록되어 있으며, 명시적인 return으로 b0를 닫았으므로 현재 block은 다시 null입니다.

따라서 CloseCallableBody() 호출에서도 종료 정보를 추가하지 않습니다.

Work 실행 전·후 구조 비교

호출 직전에는 builder와 MIR 매개변수 목록이 비어 있고, 현재 block도 아직 없습니다.
반환 직전에는 b0부터 b3까지 네 builder가 등록되어 있으며, 암시적인 return으로 b3를 닫았으므로 현재 block은 null입니다.

Work 반환 구조

이번 장에서 살펴본 LowerToMirCallable()은 현재 HIR callable의 진입 block을 만든 뒤 매개변수와 본문을 차례로 처리하고, 완성된 block을 묶어 MirCallable을 반환합니다.

Qora 예제에서는 이 과정을 통해 MirCallable Next c6과 MirCallable Work c44가 각각 만들어지는 흐름을 확인했습니다.

CloseCallableBody()

선택한 세부 흐름

본문 처리가 끝난 뒤 남아 있는 block을 확인하고, callable의 반환 계약에 맞는 종료 함수를 호출하는 흐름입니다.

LowerToMirCallable()→CloseCallableBody(mirCallableOrigin)

먼저 전체 함수를 확인합니다

먼저 현재 작성 중인 block이 있는지 확인합니다.
_currentMirBlockBuilder가 null이면 종료할 block이 없으므로 바로 반환합니다.
반면에 아직 열린 block이 있으면, 현재 변환 중인 callable이 반환 타입을 선언했는지에 따라 종료 방식을 선택합니다.

operation Read(q: Qubit): bit { return M(q); }처럼 operation도 bool, int, bit, float, angle 중 한 값을 반환할 수 있습니다.
측정한 값 자체는 bit이고, r == 1처럼 비교한 결과는 bool입니다.
반환 타입을 선언하면 모든 경로에 명시적인 값 반환이 필요하고, 반환 타입을 생략한 operation은 return;으로 일찍 종료할 수 있습니다.
다만 function의 순수성 규칙은 그대로 유지되므로, 값을 반환하는 operation도 function 안에서는 호출할 수 없습니다.

private void CloseCallableBody(MirOrigin mirCallableOrigin)
{
    if (_currentMirBlockBuilder is null)
    {
        return;
    }

    if (_hirCallable.ReturnType is not null)
    {
        MarkCurrentMirBlockUnreachable(
            MirOrigin.GeneratedFrom(
                mirCallableOrigin,
                "missing validated callable return"));
    }
    else
    {
        ReturnFromCurrentMirBlock(
            value: null,
            MirOrigin.GeneratedFrom(
                mirCallableOrigin,
                "implicit operation return"));
    }
}

아래에서는 공통 예제의 Next를 먼저 살펴본 뒤, Work로 넘어갑니다.
각 예제의 원본 코드부터 확인하고, CloseCallableBody()를 호출했을 때 어떤 분기를 거쳐 상태가 어떻게 달라지는지 따라갑니다.

1. Next에서는 이미 종료된 상태를 유지합니다

function Next(value: int): int
{
    return value + 1;
}

Next에는 return value + 1;이 있으므로, 본문 처리가 끝나면 b0에는 이미 return %v2가 기록되어 있습니다.
이때 _currentMirBlockBuilder는 null입니다.

따라서 CloseCallableBody()의 첫 번째 조건인 _currentMirBlockBuilder is null은 참입니다.
이때 return;을 실행하여 바로 함수를 마칩니다.

여기서 return;은 C# 함수인 CloseCallableBody()를 끝내는 구문이며, MIR block에 반환 명령을 추가하는 구문은 아닙니다.
Next의 반환 타입은 int이지만, ReturnType 검사에 도달하기 전에 반환하므로 기존 상태가 그대로 유지됩니다.

2. Work에서는 남아 있는 b3을 종료합니다

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

이제 같은 프로그램의 Work를 살펴봅니다. 코드 안의 Next(values[0])는 앞서 본 Next를 호출합니다.
Work에는 명시적인 return이 없으므로, 마지막 문장 H(q[0]);을 처리한 뒤에도 b3이 열린 상태로 남습니다.

이번에는 _currentMirBlockBuilder가 b3을 가리키므로 null이 아닙니다.
따라서 첫 번째 if의 return;은 실행하지 않고, 아래의 _hirCallable.ReturnType is not null 검사로 넘어갑니다.

현재 변환 중인 Work는 반환 타입을 선언하지 않았으므로 ReturnType은 null입니다.
이에 따라 조건이 거짓이 되어 else의 ReturnFromCurrentMirBlock()을 호출합니다.

여기서 ReturnType은 Work의 반환 계약을 나타냅니다.
블록 b3 자체나, Work 안에서 호출한 Next의 반환 타입을 검사하는 값은 아닙니다.

매개변수 mirCallableOrigin에는 Work h44의 출처 정보가 들어옵니다.
이 함수는 그 정보를 바탕으로 암시적인 반환을 추가하는 이유를 기록합니다.

Work 실행 전·후 구조 비교

아래에서는 같은 b3과 현재 작성 대상의 참조를 전후로 비교합니다.
b3은 목록에 그대로 남고, 종료 정보와 현재 작성 대상만 바뀝니다.

이번 장에서 살펴본 CloseCallableBody()는 본문 처리 뒤의 현재 block을 확인하고, 남아 있는 block에 필요한 종료 처리를 선택합니다.

공통 예제의 Next에서는 종료할 block이 없어 바로 반환하고, Work에서는 열린 b3에 반환값 없는 return을 기록하는 흐름을 확인했습니다.

아래 전체 코드에서 두 종료 함수의 호출부를 선택하면, 각 함수가 종료 정보를 기록하고 현재 작성 대상을 해제하는 과정을 이어서 확인할 수 있습니다.

MarkCurrentMirBlockUnreachable()

선택한 세부 흐름

현재 작성 중인 block에 MirUnreachable을 기록하여, 정상적으로 계속할 수 없는 경로의 끝을 표시하는 흐름입니다.

CloseCallableBody()→MarkCurrentMirBlockUnreachable(...)

먼저 전체 함수를 확인합니다

private void MarkCurrentMirBlockUnreachable(MirOrigin mirOrigin)
{
    var currentMirBlock = RequireCurrentMirBlock();
    currentMirBlock.MarkUnreachable(mirOrigin);
}

공통 예제에서는 호출되지 않습니다

function Next(value: int): int
{
    return value + 1;
}

위 Next는 return value + 1;을 처리하면서 block을 종료하므로, MarkCurrentMirBlockUnreachable()을 호출하지 않습니다.

아직 종료되지 않은 b0에서 시작합니다

이 함수가 block을 종료하는 과정을 살펴보기 위해, Next의 실제 실행과는 별개로 아직 종료되지 않은 b0가 현재 작성 대상으로 남아 있다고 가정합니다.
이때 _currentMirBlockBuilder는 _mirBlockBuilders[0]에 등록된 b0를 가리키며, b0의 종료 정보인 _terminator는 null입니다.

매개변수 mirOrigin에는 종료 이유를 담은 MirGeneratedOrigin 객체를 전달합니다.
아래 Reason의 "missing validated callable return"은 “값을 반환하는 callable의 반환 처리가 누락됨”을 뜻합니다.

현재 builder를 찾아 종료 요청을 전달합니다

호출된 builder 안에서 달라지는 상태

MarkUnreachable()은 block의 종료 정보를 담는 MirUnreachable 객체를 만듭니다.
아래는 그 객체가 _terminator에 저장되고, 현재 작성 대상이 해제될 때까지 호출되는 실제 코드입니다. 각 코드 위에 해당 메서드가 속한 타입을 표시했습니다.

실행 전·후 구조 비교

앞에서 지정한 내부 상태 예시의 동일한 필드를 비교합니다. 변경된 종료 정보와 현재 builder 참조에만 표시를 넣었습니다.

이번 장에서 살펴본 MarkCurrentMirBlockUnreachable()은 현재 builder를 찾아 MarkUnreachable()에 종료 이유를 전달합니다.

동작 확인용 상태 예시에서는 이 호출을 통해 b0에 MirUnreachable이 기록되고, _currentMirBlockBuilder가 null로 바뀌는 과정을 확인했습니다.

이때 목록에 저장된 b0는 유지됩니다. 해제되는 것은 현재 작성 대상에 대한 참조이며, 종료 정보는 해당 builder 안에 남습니다.

ReturnFromCurrentMirBlock()

선택한 세부 흐름

현재 작성 중인 block에 MirReturn을 기록하여 반환 경로를 끝내는 흐름입니다.

CloseCallableBody()→ReturnFromCurrentMirBlock(...)

먼저 전체 함수를 확인합니다

private void ReturnFromCurrentMirBlock(
    MirValueId? value,
    MirOrigin mirOrigin)
{
    var currentMirBlock = RequireCurrentMirBlock();
    currentMirBlock.Return(value, mirOrigin);
}

먼저 현재 작성 중인 block builder를 currentMirBlock에 담습니다.
이어서 그 builder의 Return()에 반환값 value와 출처 정보 mirOrigin을 전달합니다.

Work의 반환 경로를 끝내는 과정

function Next(value: int): int
{
    return value + 1;
}

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

여기서는 Work의 마지막 H(q[0]);까지 처리된 상태에서 시작합니다.
현재 작성 중인 builder는 b3이며, 아직 이 block을 끝내는 명령은 없습니다.

이번 호출의 value는 null이므로 값을 돌려주지 않는 return을 기록합니다.
mirOrigin에는 이 반환이 Work h44에 자동으로 추가된 것임을 나타내는 출처 정보가 들어옵니다.

현재 builder에 두 인수를 전달합니다

builder가 반환 명령을 기록합니다

다음 코드는 MirBlockBuilder의 Return()과 그 함수가 호출하는 Terminate()입니다.
여기서 this는 반환 명령을 기록할 MirBlockBuilder b3입니다.

lowerer가 현재 작성 대상을 비웁니다

OnMirBlockTerminated()는 HirCallableToMirLowerer의 함수입니다.
전달받은 terminatedMirBlock이 현재 작성 대상으로 지정된 객체인지 확인합니다.

호출 전·후 같은 구조를 비교합니다

아래는 지역 변수 currentMirBlock을 확보한 뒤, currentMirBlock.Return(value, mirOrigin)을 호출하기 전과 돌아온 직후의 비교입니다.
이번 호출에서 바뀐 b3의 종료 명령과 _currentMirBlockBuilder를 강조했습니다.

반환 명령 기록↓

_currentMirBlockBuilder가 null로 바뀌어도 지역 변수 currentMirBlock은 같은 b3를 가리킵니다.
따라서 이 변화는 builder의 삭제가 아니라, lowerer의 현재 작성 대상을 비운 것입니다.

이번 장에서 살펴본 ReturnFromCurrentMirBlock()은 현재 builder를 확보하고, 전달받은 반환값과 출처 정보로 그 block의 반환 경로를 끝냅니다.

Work 예제에서는 b3의 _terminator에 Value = null인 MirReturn이 기록됩니다.
이어서 종료 알림을 받은 lowerer가 _currentMirBlockBuilder를 null로 바꾼다는 점을 확인했습니다.

이로써 b3에는 반환 명령이 기록되고, 현재 작성 대상은 비워집니다.
종료된 builder 자체는 _mirBlockBuilders[3]에 보존됩니다.

먼저 전체 함수를 확인합니다

아래 코드는 세부 흐름을 확인할 LowerParameters() 전체입니다.
먼저 매개변수를 순회하고 타입에 맞는 helper를 선택하는 순서를 확인한 뒤, Next h6을 대입하여 각 코드 범위가 만드는 상태를 살펴봅니다.
테두리와 세부 흐름 보기 뱃지가 있는 호출부를 선택하면 해당 함수의 실행 흐름으로 이동합니다. 

private void LowerParameters()
{
    var requiredArrayLengths =
        _hirArtifact.Model.RequiredArgLengths(_hirCallable.Id);

    for (var hirParameterIndex = 0;
         hirParameterIndex < _hirCallable.Parameters.Count;
         hirParameterIndex++)
    {
        var hirParameter =
            _hirCallable.Parameters[hirParameterIndex];

        var hirParameterSymbol = RequireHirDeclarationSymbol(
            hirParameter.Id,
            $"parameter `{hirParameter.Name}`");
        var mirParameterOrigin = MirOriginFor(hirParameter);

        _currentFlowState.TrackDeclaredHirSymbol(
            hirParameterSymbol.Id);

        if (hirParameter.Type == QType.Qubit)
        {
            LowerQubitParameter(
                hirParameter,
                hirParameterSymbol.Id,
                mirParameterOrigin);
            continue;
        }

        LowerClassicalParameter(
            hirParameter,
            hirParameterSymbol.Id,
            mirParameterOrigin,
            requiredArrayLengths);
    }
}

LowerClassicalParameter()

선택한 세부 흐름

고전 매개변수 하나를 MIR 값과 매개변수 객체로 등록하는 흐름입니다.

LowerParameters()→LowerClassicalParameter(...)

HIR의 고전 매개변수 하나를 MIR 값과 MirClassicalParameter로 등록하는 함수입니다.
아래 실행에서는 Next(value: int)의 value h0 하나를 처리합니다.

먼저 전체 함수를 확인합니다

아래 코드는 세부 흐름을 확인할 LowerClassicalParameter() 전체입니다.
먼저 MIR 타입과 값을 만들고 필요한 storage를 준비한 뒤, 매개변수 객체를 등록하는 순서를 확인합니다.
테두리와 세부 흐름 보기 뱃지가 있는 호출부를 선택하면 CreateMirParameterStorage()의 실행 흐름으로 이동합니다. 

private void LowerClassicalParameter(
    HirParameter hirParameter,
    SymbolId hirParameterSymbolId,
    MirOrigin mirParameterOrigin,
    IReadOnlyDictionary<string, long>? requiredArrayLengths)
{
    var mirParameterType = hirParameter.IsArray
        ? MirType.Array(hirParameter.Type, hirParameter.RegisterSize)
        : MirType.Scalar(hirParameter.Type);

    var mirParameterValue = CreateMirValue(
        mirParameterType,
        hirParameterSymbolId,
        mirParameterOrigin);

    var (mirArrayStorage, minimumLength) =
        CreateMirParameterStorage(
            hirParameter,
            hirParameterSymbolId,
            mirParameterOrigin,
            requiredArrayLengths);

    _currentFlowState.CurrentMirValueByHirSymbolId[hirParameterSymbolId] = mirParameterValue.Id;

    var mirParameter = mirArrayStorage is null
        ? MirClassicalParameter.Scalar(
            hirParameter,
            mirParameterValue)
        : MirClassicalParameter.Array(
            hirParameter,
            mirParameterValue,
            mirArrayStorage,
            minimumLength);

    _mirParameters.Add(mirParameter);
}

이제 value h0를 대입하여 위 코드의 상태 변화를 순서대로 따라갑니다.

private void LowerStatements(IReadOnlyList<HirStatement> hirStatements)
{
    for (var hirStatementIndex = 0;
         hirStatementIndex < hirStatements.Count;
         hirStatementIndex++)
    {
        if (_currentMirBlockBuilder is null)
        {
            for (;
                 hirStatementIndex < hirStatements.Count;
                 hirStatementIndex++)
            {
                MarkUnreachableDeclarations(
                    hirStatements[hirStatementIndex]);
            }
            return;
        }

        LowerStatement(hirStatements[hirStatementIndex]);
    }
}

1. Next의 본문을 처리하는 과정

function Next(value: int): int
{
    return value + 1;
}

hirStatements에는 return value + 1; 한 문장만 들어 있으며, 시작할 때 현재 block은 b0입니다.
따라서 바깥 for는 한 번만 실행됩니다.

Next 호출 전·후 비교

이 함수는 문장을 처리한 helper의 내부 결과를 펼치지 않고, 다음 반복을 결정할 때 직접 확인하는 값만 보여줍니다.
따라서 LowerStatement()를 호출하기 전의 목록·인덱스·현재 block과, 호출이 끝난 뒤 달라진 인덱스·현재 block을 같은 순서로 비교합니다.

2. Work의 본문을 처리하는 과정

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

먼저 Work의 네 block을 확인합니다

b0, b1, b2, b3는 Work 안의 MIR block을 구분하는 식별자입니다.
각 block에는 순서대로 처리할 MIR 명령이 담기며, 끝에서는 다음 block으로 이동하거나 반환합니다.
아래 그림은 본문을 변환하면서 만들어지는 연결을 미리 보여줍니다. 상자 안에는 이해를 돕기 위해 대응하는 Qora 문장을 적었습니다.

화살표는 프로그램의 실행 경로를 나타냅니다.
조건이 참이면 b0 → b1 → b3, 거짓이면 b0 → b2 → b3으로 이어지며, b1과 b2를 차례로 실행하지는 않습니다.
이번 예제에서는 Next(0)이 1을 반환하므로 참 경로를 지나지만, MIR에는 두 경로가 모두 표현됩니다.

반면에 컴파일러는 참·거짓 본문을 모두 변환합니다.
처음에는 b0만 있으며, if문을 변환하는 동안 b1, b2, b3가 추가됩니다.
아래에서는 이 변환 과정에서 LowerStatements()가 받은 문장 목록을 어떻게 처리하는지 살펴봅니다.

Work를 변환하는 동안 이 함수가 받는 문장 목록은 세 가지입니다.
최상위 본문의 다섯 문장, if의 참 본문에 있는 X(q[0]), 문장이 없는 거짓 본문입니다.

Work에서 이 함수가 받은 세 번의 호출

아래 비교는 세 호출을 서로 섞지 않습니다.
각 호출마다 전달된 목록과 인덱스, 호출 전·후의 현재 block만 보여주며, block을 만들거나 합치는 helper 내부 과정은 포함하지 않습니다.

이번 장에서 살펴본 LowerStatements()는 받은 문장 목록을 순서대로 순회하고, 현재 block이 열려 있는 동안 각 문장을 LowerStatement()에 전달합니다.

Qora 예제에서는 Next의 반환문과 Work의 최상위·참 본문이 전달되지만, 빈 거짓 본문에서는 LowerStatement()가 호출되지 않는다는 점을 확인했습니다.

아래 전체 코드에서 LowerStatement() 호출부를 선택하면 HIR 문장 하나가 타입에 맞는 helper로 전달되는 세부 흐름을 다시 확인할 수 있습니다.

세부 흐름을 선택합니다

LowerStatements()의 상세 호출

private void LowerStatements(IReadOnlyList<HirStatement> hirStatements)
{
    for (var hirStatementIndex = 0;
         hirStatementIndex < hirStatements.Count;
         hirStatementIndex++)
    {
        if (_currentMirBlockBuilder is null)
        {
            for (;
                 hirStatementIndex < hirStatements.Count;
                 hirStatementIndex++)
            {
                MarkUnreachableDeclarations(
                    hirStatements[hirStatementIndex]);
            }
            return;
        }

        LowerStatement(hirStatements[hirStatementIndex]);
    }
}

LowerStatement()

선택한 세부 흐름

HIR 문장 하나의 타입을 확인하고 담당 lowering helper를 선택하는 흐름입니다.

LowerStatements(...)→LowerStatement(...)

LowerStatement()는 호출될 때마다 HIR 문장 하나만 받습니다.
switch는 hirStatement의 실제 HIR 타입과 같은 case 하나를 고르고, 그 case에 적힌 helper를 호출합니다.
helper 호출 뒤의 return;은 현재 LowerStatement() 실행을 끝냅니다.

Qora 예제에서 전달되는 문장

function Next(value: int): int
{
    return value + 1;
}

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

공통 예제에서 이 함수는 모두 일곱 번 실행됩니다.
Next의 반환문 한 번과 Work의 문장 여섯 번을 각각 한 개씩 받습니다.

아래 오른쪽 카드의 번호는 실제 호출 순서입니다.
반면에 왼쪽 case가 적힌 순서는 소스 코드의 배치일 뿐이며, 한 번 호출될 때는 실제 HIR 타입과 같은 case 하나만 실행합니다.

if 안의 X(q[0]);은 독립된 문장이므로 여섯 번째 호출로 다시 들어옵니다.
반면에 대입문 안의 Next(values[0])은 표현식이므로 별도의 호출로 세지 않습니다.

Qora 예제의 실제 호출 순서

위 카드는 switch의 각 case가 어떤 문장을 선택하는지 보여주었습니다.
아래 트리는 Qora 예제에서 LowerStatement()이 받은 일곱 문장을 실제 호출 순서대로 정리합니다.

일곱 번의 실행은 각각 표시된 helper 하나를 호출한 뒤 return;으로 끝납니다.

이번 장에서 살펴본 LowerStatement()는 전달받은 HIR 문장 한 개의 타입을 확인하고, 일치하는 helper 하나를 호출한 뒤 종료합니다.

Qora 예제에서는 일곱 문장이 각각 해당 helper 하나로 분기되고, 모든 호출이 값을 반환하지 않고 종료된다는 점을 확인했습니다.
