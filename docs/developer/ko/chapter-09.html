최종 HIR에서 최초 MIR로

공통 예제가 ToMir()에 들어가 최초 MirSnapshot이 될 때까지

이전 주제: 8장 목차전체 목차
다음: Callable lowering →

아래 소스가 의미 분석을 마치면 QoraCompiler.CompileOnCurrentThread()은 완성된 HIR을 ToMir()에 전달합니다.
그 호출부터 실제 인수와 지역 변수의 값을 대입한 채 LowerHirArtifact(), MirProgram, MirSnapshot.CreateLowered()로 이어지는 순서를 추적합니다.

이번 장에서 실제로 처리할 소스

function Next(value: int): int
{
    return value + 1;
}

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

현행 CLI로 이 소스를 컴파일하면 최종 HIR의 두 callable은 Next h6과 Work h44입니다.
같은 callable을 MIR로 내리면 각각 Next c6과 Work c44가 됩니다.
뒤에서 h6, c6, h44, c44가 다시 나오더라도 모두 위의 두 선언을 가리킵니다.

ToMir() 호출 직전의 실제 상태

이 소스는 먼저 구문 분석, 이름 해소, 타입·호출 계약 검사, 단형화, 최종 검증을 통과합니다.
다만 그 다음 코드를 읽기 전에 CLI가 컴파일러에 넘기는 인수부터 고정해야 합니다.
Program.cs의 실제 호출은 다음과 같으며, 세 번째 인수를 생략하므로 instrumentation은 null입니다. 

// Program.cs의 CLI 진입부
var compilation = QoraCompiler.Compile(
    source,
    new CompilationOptions(baseDir, sourcePath));

// 위 호출에서 확정되는 값
// options.OutputPlan = CompilationOutputPlan.Default
// options.OutputPlan.RequiresMir = true
// instrumentation = null

CompilationOptions 생성자에 별도 출력 계획을 주지 않았으므로 CompilationOutputPlan.Default가 선택되고, 이 계획의 RequiresMir는 true입니다.
따라서 CompileOnCurrentThread()의 MIR 분기를 건너뛰지 않으며, instrumentation?.MirLowering의 실제 값은 null입니다.
이 값을 대입하고 이 장의 범위를 벗어나는 materialization·OpenQASM 처리를 제외하면 실행 경로는 아래 네 문장으로 정리됩니다. 

// CompileOnCurrentThread()의 관련 코드에 위 예제값을 대입한 경로
// specializedValidation = 이 소스의 단형화 후 검증 artifact
hirBuilder.AnalyzeEffects(specializedValidation);

// builtHir.EffectAnalysis.Source.Program.Callables
// = [Next h6, Work h44]
var builtHir = hirBuilder.Build();

// instrumentation?.MirLowering의 실제 값이 null이므로 다음과 같습니다.
var mir = builtHir.ToMir(traceSink: null);

// mir.Program.Callables = [Next c6, Work c44]
// mir.Program.EntryPoint = Work c44
_ = mir.Analyses.Effects;

여기서 builtHir.EffectAnalysis는 최종 HIR 트리와 그 트리에 대응하는 의미 모델을 함께 가진 HirSemanticArtifact입니다.
다음 절은 바로 세 번째 문장인 builtHir.ToMir(traceSink: null) 안으로 들어갑니다.

이 시점에 하지 않는 일 ToMir()은 Next라는 문자열을 검색하거나 value + 1의 타입을 다시 추론하지 않습니다.
필요한 이름 연결과 타입 정보는 바로 위의 hirArtifact.Model에 이미 확정되어 있습니다.

ToMir()에서 최종 artifact 꺼내기

이제 실제 진입 함수를 처음부터 끝까지 읽습니다.
첫 번째 인수 hirCompilation에는 방금 만든 builtHir이 들어가고, 두 번째 인수 traceSink에는 기본 CLI 기준 null이 들어갑니다. 

public static MirSnapshot ToMir(
    this HirCompilation hirCompilation,
    IMirLoweringTraceSink? traceSink = null)
{
    // 예제값: hirCompilation = builtHir
    ArgumentNullException.ThrowIfNull(hirCompilation);

    // 예제값: hirArtifact.Source.Program.Callables = [Next h6, Work h44]
    // 예제값: hirArtifact.Source.Program.EntryCallable = Work h44
    var hirArtifact = hirCompilation.EffectAnalysis
        ?? throw new InvalidOperationException(
            "MIR lowering requires the compilation's final effect-analyzed HIR");

    // 예제 호출: LowerHirArtifact(hirArtifact, null)
    return LowerHirArtifact(hirArtifact, traceSink);
}

분기는 하나뿐입니다. EffectAnalysis가 없으면 예외가 발생하고, 이 예제처럼 값이 있으면 그 정확한 객체 하나를 LowerHirArtifact(hirArtifact, null)에 전달합니다.
따라서 다음 함수가 받는 HIR 트리와 의미 모델은 서로 다른 단계에서 임의로 조합한 값이 아닙니다.

트리와 의미 모델이 함께 이동하는 이유

곧 처리할 Next(values[0]) 호출을 예로 들면, 트리에는 호출식의 모양이 있고 의미 모델에는 그 호출이 Next h6 선언을 가리킨다는 연결이 있습니다.
LowerPureCall()은 두 정보를 함께 읽어 new MirCallableId(6)을 만들므로, 트리와 모델 중 하나만 다른 HIR 세대의 값이어서는 안 됩니다. HirSemanticArtifact 하나만 전달하는 현재 경계가 그 잘못된 조합을 처음부터 만들 수 없게 합니다.

LowerHirArtifact()의 바깥 호출 흐름

아래는 현재 구현의 함수 전체이며, 주석만 이 예제의 실제 값으로 바꾸어 읽기 쉽게 표시했습니다.
여기서는 callable 내부 명령으로 들어가기 직전까지, 목록이 어떻게 채워지고 진입 callable이 어떻게 선택되는지를 확인합니다.
내부 변환은 10장과 11장에서 같은 실행을 계속 추적합니다. 

private static MirSnapshot LowerHirArtifact(
    HirSemanticArtifact hirArtifact,
    IMirLoweringTraceSink? traceSink)
{
    // 예제값: hirArtifact = ToMir()가 꺼낸 최종 effect-analysis artifact
    // 예제값: traceSink = null
    ArgumentNullException.ThrowIfNull(hirArtifact);

    // 예제값: hirSnapshot.Program에 Next h6, Work h44가 있습니다.
    var hirSnapshot = hirArtifact.Source;
    var hirProgram = hirSnapshot.Program;

    // 예제값: hirEntryCallable = Work h44
    var hirEntryCallable = hirProgram.EntryCallable
        ?? throw new InvalidOperationException(
            "validated HIR must contain an operation before MIR lowering");

    // 반복 시작 전 예제값: [], null
    var mirCallables = new List<MirCallable>();
    MirCallable? mirEntryCallable = null;

    // 예제 반복 순서: 1회차 Next h6, 2회차 Work h44
    foreach (var hirCallable in hirProgram.Callables)
    {
        var mirCallableLowerer = new HirCallableToMirLowerer(
            hirCallable,
            hirArtifact,
            traceSink);

        // 1회차 결과: Next c6
        // 2회차 결과: Work c44
        var mirCallable = mirCallableLowerer.LowerToMirCallable();

        // 1회차: [] -> [Next c6]
        // 2회차: [Next c6] -> [Next c6, Work c44]
        mirCallables.Add(mirCallable);

        // 1회차: ReferenceEquals(Next h6, Work h44) = false
        // 2회차: ReferenceEquals(Work h44, Work h44) = true
        if (ReferenceEquals(hirCallable, hirEntryCallable))
            mirEntryCallable = mirCallable;
    }

    // 예제값: EntryPoint = Work c44
    // 예제값: Callables = [Next c6, Work c44]
    var mirProgram = new MirProgram(
        mirEntryCallable
            ?? throw new InvalidOperationException(
                "validated HIR entry callable must be lowered into MIR"),
        mirCallables);

    // 예제 반환값: Stage가 Lowered인 최초 MirSnapshot
    return MirSnapshot.CreateLowered(mirProgram);
}

첫 반복에서는 새 lowerer가 Next h6을 받아 Next c6을 반환합니다.
이 객체는 목록에 추가되지만 HIR 진입점 Work h44와 같은 객체가 아니므로 mirEntryCallable은 여전히 null입니다.
두 번째 반복에서는 Work h44을 받은 별도의 lowerer가 Work c44을 반환합니다.
이번에는 ReferenceEquals(hirCallable, hirEntryCallable)가 참이므로, 방금 목록에 넣은 바로 그 Work c44 객체가 mirEntryCallable에도 저장됩니다.

foreach 반복에 따른 지역 변수 변화
시점hirCallablemirCallablesmirEntryCallable
반복 전없음[]null
첫 반복 후Next h6[Next c6]null
둘째 반복 후Work h44[Next c6, Work c44]Work c44

다음 소비처인 MirProgram 생성자는 EntryPoint가 Callables에 들어 있는 정확히 같은 객체인지 확인합니다.
이 예제에서는 목록의 두 번째 객체와 EntryPoint가 모두 같은 Work c44이므로 검사를 통과합니다. 

MirProgram
├─ EntryPoint ───────────────┐
│  └─ Work c44               │ 같은 객체

h6 → c6, h44 → c44가 되는 지점

숫자가 유지되는 이유는 이름이 우연히 같아서가 아닙니다.
각 반복에서 lowerer 생성자가 HIR callable ID의 정수값을 읽어 새 MIR callable ID를 직접 만듭니다. 

public HirCallableToMirLowerer(
    HirCallable hirCallable,
    HirSemanticArtifact hirArtifact,
    IMirLoweringTraceSink? traceSink)
{
    // 1회차 hirCallable = Next h6, 2회차 = Work h44
    _hirCallable = hirCallable;
    _hirArtifact = hirArtifact;

    // 1회차 new MirCallableId(6)  = c6
    // 2회차 new MirCallableId(44) = c44
    _mirCallableId =
        new MirCallableId(hirCallable.Id.Value);
    _traceSink = traceSink;
}

HirNodeId h6과 MirCallableId c6은 서로 다른 타입입니다.
정수 부분만 보존하여 단계 사이의 대응을 읽기 쉽게 만든 것이며, HIR 객체를 MIR 객체로 재사용한 것은 아닙니다.

새 MIR 객체가 최종 HIR artifact를 이어받는 과정

callable 내부에서 만들어지는 Origin은 MirOriginFor(sourceHirNode)를 통과합니다.
이 함수는 현재 lowerer가 받은 _hirArtifact와 그 artifact가 실제로 소유한 HIR 노드를 함께 묶습니다. 

private MirOrigin MirOriginFor(HirNode sourceHirNode) =>
    // 예제: Next의 이항식 h3이라면 (_hirArtifact, h3)을 묶습니다.
    MirOrigin.FromHirNode(_hirArtifact, sourceHirNode);

그 결과 MirProgram은 모든 callable·block·instruction·값의 Origin이 하나의 HIR artifact로 끝나는지 검사한 뒤 그 artifact를 자신의 HirArtifact로 확정합니다.
마지막 소비처인 CreateLowered()는 이 프로그램을 검증하고 최초 snapshot을 만듭니다. 

internal static MirSnapshot CreateLowered(MirProgram program) =>
    new(program);

private MirSnapshot(MirProgram program)
{
    // 예제값: program.EntryPoint = Work c44
    // 예제값: program.Callables = [Next c6, Work c44]
    ArgumentNullException.ThrowIfNull(program);

    var hirArtifact = program.HirArtifact;

    if (!hirArtifact.IsReadyForMirLowering)
    {
        throw new ArgumentException(
            "MIR lowering requires a HIR artifact ready for MIR lowering.",
            nameof(program));
    }
    QoraMirVerifier.VerifyOrThrow(program);

    Stage = MirStage.Lowered;
    Program = program;
    HirArtifact = hirArtifact;
    PreviousSnapshot = null;
    Analyses = new MirAnalysisStore(program);
}

따라서 이 장의 최종 반환값은 Stage = Lowered, Program.EntryPoint = Work c44, Program.Callables = [Next c6, Work c44]인 MirSnapshot입니다.
이 snapshot은 곧바로 QoraCompiler의 mir 변수에 저장되고, 다음 줄의 mir.Analyses.Effects가 최초 소비자가 됩니다.

예제 추적 뒤에 정리하는 경계의 책임

HIR→MIR 경계가 실제로 수행한 작업
구분이 예제에서 확인한 내용
입력 선택builtHir.EffectAnalysis라는 최종 artifact 하나를 선택합니다.
전체 순회Next h6, Work h44 순서로 각각 별도 lowerer를 실행합니다.
프로그램 조립[Next c6, Work c44]와 그 목록 안의 정확한 Work c44 진입점을 묶습니다.
snapshot 생성검증된 프로그램을 Stage = Lowered인 최초 MirSnapshot으로 봉인합니다.
다음 소비처mir.Analyses.Effects와 이후 MIR 변환·target lowering이 이 snapshot을 읽습니다.

여기까지는 프로그램 바깥 경계만 추적했습니다.
다음 장에서는 같은 foreach의 첫 반복과 둘째 반복 안으로 들어가, 새 lowerer의 필드가 어떤 값으로 시작하고 LowerToMirCallable()이 매개변수·본문·block을 어떤 순서로 채우는지 확인합니다.
