キュービット identity とバージョン

q0 は維持され、v0 → v1 → v2 → v3 が生まれる理由

← 前：配列 Storage全章目次
次：Basic Block →

キュービットにゲートを適用しても、ソースの q 宣言が新しいリソースへ変わるわけではありません。
MIR は同じ論理キュービットリソースであることを q0 で維持しながら、ゲートを通って変化した計算状態を v0、v1 のように区別します。
下のコードで、長さ 1 のキュービットリソース q が四つのバージョンへ進む流れだけを確認します。

確認する Qora コード

function Next(value: int): int
{
    return value + 1;
}

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

q は一つのキュービットを持つ長さ 1 の論理リソースです。
条件が true なら最初に X を適用し、条件に関係なく最後に H を適用します。
この例を実行すると条件は true ですが、MIR lowering は Next の呼び出し結果を事前計算しないため、true・false 両方の経路を保持します。

バージョン全体の流れ

すべての項目が q0 で始まるのは、最初に宣言した論理キュービットリソース q を使い続けるためです。
後ろのバージョンだけが変わるのは、各地点でどのゲートまで通過したかを区別する必要があるためです。

割り当て：最初の状態 q0.v0

use q = Qubit[1]; が長さ 1 のキュービットリソースを割り当てると、MIR はそのリソースへ q0 という identity を与えます。
q0 は個別要素 q[0] の番号ではなく、callable 内の q 宣言全体を区別する番号です。実際の要素は q0.v0[0] のように別のインデックスで選択します。
したがって、ハードウェア上の物理キュービット番号ではありません。
同時に、まだゲートを通っていない最初のバージョン v0 が付き、q0.v0 になります。

後に出てくる q0.v1、q0.v2、q0.v3 は、すべて同じ論理リソース q0 に関する記録です。
キュービットリソースをさらに三つ割り当てる意味ではありません。

分岐：true 経路だけが X を通る

if 分岐へ入るとき、両方の経路は同じ入力 q0.v0 から始まります。
true 経路では X が q0.v0 を入力とし、ゲート通過後の結果を新しいバージョン q0.v1 として記録します。
一方、false 経路は X を実行しないため、q0.v0 をそのまま維持します。

このようにバージョンを分けると、MIR を読む解析は「この値は X を通った状態か」を命令順序から再推測せずに判断できます。

合流：二つの可能性を q0.v2 にまとめる

if が終わると、true 経路と false 経路は再び一つに合流します。
しかし一方は q0.v1、もう一方は q0.v0 なので、合流点でどちらか一つを無条件に選べません。
MIR はこの二つの可能性を Phi でまとめ、q0.v2 を作ります。

Phi は新しいゲートではなく、新しいキュービットも割り当てません。
実行が b1 から来たなら q0.v1、b2 から来たなら q0.v0 という制御フローの選択を、一つの名前 q0.v2 で表します。

合流後の H：q0.v3

最後の文 H(q[0]); は if の外側にあるため、二つの経路が合流した後に実行されます。
したがって入力は特定経路の q0.v0 や q0.v1 ではなく、両方の可能性を表す q0.v2 です。
H を通った結果は、再び新しいバージョン q0.v3 になります。

まとめ

identity と version q0 は最初に割り当てた論理キュービットリソース q の identity なので維持されます。
v0 → v1 → v2 → v3 は、そのリソースがどのゲートと分岐合流を通ったかを表す計算バージョンです。
したがって q0.v3 は四つ目のリソースではなく、同じ q0 の最新状態です。

次の章では、これらのバージョンを入れる Basic Block を確認します。
同じ if が b0、b1、b2、b3 に分かれる理由を、全体の流れに沿って確認します。
