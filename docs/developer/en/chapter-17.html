CFG Successors and Predecessors

Reading terminator transfers as a graph in both directions

← Previous: MIR snapshotsAll chapters
Next topic: Reachability and dominance →

A CFG is a graph of transfers between blocks.
Instead of constructing another execution structure, Qora computes this graph by reading the terminator already stored at the end of each block.

Qora code used to build the CFG

function Next(value: int): int
{
    return value + 1;
}

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

Chapter 14 split this conditional into four blocks.
b0 evaluates the condition, b1 executes the true body, and b2 represents the false path. The two paths join at b3, which then executes H. 

          ┌──→ b1: X ──┐
b0: condition           ├──→ b3: H → return
        └──→ b2 ─────┘

Terminators are the source of the arrows

Every block has one terminator at its end.
Ordinary MIR instructions compute values or apply gates; a terminator decides where execution moves after the block ends. 

b0.Terminator = Branch
├─ condition true  → b1
└─ condition false → b2

b1.Terminator = Jump → b3
b2.Terminator = Jump → b3
b3.Terminator = Return

Branch has two destinations, while Jump has one.
Return ends callable execution and therefore has no next block. The CFG is a tabular representation of these facts.

Collecting next blocks produces the successor table

A successor is a block that execution can enter after the current block.
The analysis reads the destinations referenced by each block's terminator and creates the following table. 

Successors
├─ b0 → [b1, b2]
├─ b1 → [b3]
├─ b2 → [b3]
└─ b3 → []

b0 has two successors because the condition can select either destination.
Both b1 and b2 move to join block b3; b3 returns and therefore has an empty list.

Important Having two successors does not mean that both blocks execute.
A CFG represents every path that may be selected; one actual execution selects only the path matching the condition.

Reversing the arrows produces the predecessor table

A predecessor is a previous block that can transfer into the current block.
It is not recomputed from another source; the completed successor arrows are simply reversed. 

Successor arrow                 Reversed predecessor relation
b0 → b1                          b1 ← b0
b0 → b2                          b2 ← b0
b1 → b3                          b3 ← b1
b2 → b3                          b3 ← b2

Predecessors
├─ b0 ← []
├─ b1 ← [b0]
├─ b2 ← [b0]
└─ b3 ← [b1, b2]

No block enters entry block b0, so its list is empty.
Join block b3 has two predecessors because both true-path b1 and false-path b2 enter it.

Deriving predecessors from successors keeps both tables based on one source of truth.
This avoids inconsistencies such as recording b1 → b3 on one side while omitting b3 ← b1 on the other.

Both tables form the callable's CFG snapshot

When the CFG of Work is requested from the current snapshot, the analysis store reads the blocks and terminators of Work.
The result is a MirControlFlowSnapshot containing successors and predecessors. 

MirSnapshot
└─ CFG of Work
   └─ MirControlFlowSnapshot
      ├─ SourceCallable = Work
      ├─ EntryBlock = b0
      ├─ SuccessorsOf(b0) = [b1, b2]
      └─ PredecessorsOf(b3) = [b1, b2]

This CFG snapshot is not a second block tree to execute.
It is derived information that continues to reference the original blocks of Work while making their relationships efficient to query.

Summary Terminators are the authoritative source of block transfers, and the successor table records those transfers in the forward direction.
The predecessor table reverses the same arrows. Both results are collected into one callable-specific CFG snapshot that supports later MIR analyses.
