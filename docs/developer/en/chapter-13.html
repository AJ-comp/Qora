Qubit Identity and Versions

Why q0 remains while v0 → v1 → v2 → v3 is created

← Previous: Array storageAll chapters
Next: Basic blocks →

Applying a gate to a qubit does not replace the source declaration q with a new resource.
MIR preserves the fact that it is the same logical qubit resource through q0, while versions such as v0 and v1 distinguish the computational states produced by gates.
This chapter follows only how the length-1 qubit resource q advances through four versions.

Qora code under examination

function Next(value: int): int
{
    return value + 1;
}

operation Work()
{
    var values: int[] = [0];
    use q = Qubit[1];

    values[0] = Next(values[0]);

    if (values[0] == 1)
    {
        X(q[0]);
    }

    H(q[0]);
}

q is a length-1 logical resource containing one qubit.
If the condition is true, the program applies X first. It applies H at the end regardless of the condition.
Although the condition is true when this example runs, MIR lowering does not precompute the result of calling Next, so it preserves both the true and false paths.

Complete version flow

Every entry begins with q0 because the program continues to use the logical qubit resource q that was declared initially.
Only the version suffix changes because MIR must distinguish which gates the resource has passed through at each point.

Allocation: initial state q0.v0

When use q = Qubit[1]; allocates a length-1 qubit resource, MIR gives that resource the identity q0.
q0 is not the number of element q[0]. It identifies the entire q declaration within the callable. An actual element is selected with a separate index, as in q0.v0[0].
It therefore does not represent a physical hardware-qubit number.
MIR also attaches initial version v0, which has not passed through any gate, producing q0.v0.

The later values q0.v1, q0.v2, and q0.v3 all describe the same logical resource q0.
They do not mean that three more qubit resources are allocated.

Branch: only the true path passes through X

Both paths begin with the same input, q0.v0, when execution enters the if branch.
On the true path, X takes q0.v0 as input and records the result after the gate as new version q0.v1.
The false path does not execute X, so it keeps q0.v0 unchanged.

Separating the versions lets an analysis that reads MIR determine whether a value has passed through X without reconstructing the instruction order.

Join: combine both possibilities as q0.v2

After the if, the true and false paths join again.
One path has q0.v1 and the other has q0.v0, so the join point cannot unconditionally select either version.
MIR combines both possibilities with a Phi and creates q0.v2.

A Phi is not a new gate and does not allocate a new qubit.
It gives one name, q0.v2, to the control-flow choice: q0.v1 when execution came from b1, or q0.v0 when it came from b2.

H after the join: q0.v3

The final statement, H(q[0]);, is outside the if, so it runs after both paths have joined.
Its input is therefore q0.v2, which represents both possibilities, rather than path-specific q0.v0 or q0.v1.
The result after H becomes another new version, q0.v3.

Summary

Identity and version q0 remains because it is the identity of the initially allocated logical qubit resource q.
v0 → v1 → v2 → v3 are computational versions that record which gates and branch joins that resource has passed through.
Thus, q0.v3 is not a fourth resource; it is the latest state of the same q0.

It follows the overall flow to show why the same if is split into b0, b1, b2, and b3.
