Qora コンパイルパイプライン設計

ソースが source-shaped HIR、SSA/CFG MIR、typed target、OpenQASM 出力まで進む基準フロー

Qora は、パーサエンジン（Janglim）の上に載る小さなフロントエンドと、その上にQora が完全に所有する マルチパスのミドルエンドから成ります。コンパイルは、小さく単一目的なパスの一直線です。各パスは プログラムをある形で受け取り、ちょうど 1 つの仕事だけをこなし、少しだけ仕上がったプログラムを次のパスへ渡します — 最後のパスが OpenQASM 3 を出力するまで。本ドキュメントはその一直線を最初から最後まで 1 ステージずつ辿り、 コンパイラ出力と説明用の短い MIR sketch を組み合わせます。

0例 — すべてのパスに触れる 1 ファイル

ソース向けの各ステージが実際に働く様子を見るため、名前空間と 量子ビット配列パラメータ（Qubit[]）、呼び出しを 1 つのプログラムに詰め込みます: 

namespace Prep {
    operation Fanout(q: Qubit[]) {        // 配列長は呼び出しごとに決まる
        for i in 0..q.Count-1 { H(q[i]); }
    }
}

operation Main() {
    use reg = Qubit[3];
    Prep.Fanout(reg);                    // 名前空間をまたぐ呼び出し
    var r: bit = M(reg[0]);
}

名前がパスを通り抜けて変わっていく様子を追ってください。Fanout は名前空間を得 （Prep.Fanout）、具体的なサイズを得た後（Prep.Fanout__sz3）、最後に OpenQASM 用に平坦化されます（Prep_Fanout__sz3）。各変化を下記の 1 パスずつが担当します。

12 つの世界 — エンジンが止まり Qora が始まる場所

コンパイラ全体で境界はちょうど 1 つだけです。その左には Janglim パーサエンジンがあります — 文法・レクサ、そしてテキストを構文木に変える仕事を所有します。右には Qora があります — プログラムに意味を与え、検査し、変換し、出力するすべてのパスがここにあります。2 つの世界は 1 つの関数で出会います — ローワリング（lowering） — この関数はエンジンの木をちょうど一度だけ読み、二度と振り返りません。

ソース → AST  │ エンジン (Janglim)
Qora │  HIR → SSA/CFG MIR → typed target → OpenQASM
なぜ境界をこれほど鋭く保つのか? Qora が扱うべきすべて — 型、逆演算、ジェネリック、名前の安全性 — は、エンジンの木ではなく Qora 自身の IR 上で処理されます。だからエンジンは量子について何も知らない汎用パーサのまま でいられ、Qora は文法に触れずに機能（新しいパス）を追加できます。エンジンに依存する唯一の地点はローワリング であり、残りのコンパイラはパーサを丸ごと差し替えても生き延びます。

2Parse — ソースから AST へ（エンジンの仕事）

in: ソーステキスト  ·  out: 構文木  ·  担当: Janglim エンジン

エンジンは Qora の文法からレクサと LALR パーサを作り、ソースをパース木に変えます。この段階 には意味がありません — Prep.Fanout は 3 つのトークン （Prep、.、Fanout）であり、呼び出しとゲートは同じ見た目です。 例の実際の木: 

Nonterminal : Program
  Nonterminal : Namespace
    Terminal : Prep
    Nonterminal : Operation
      Terminal : Fanout
      Nonterminal : Param
        Nonterminal : ArrayType
          Terminal : Qubit
        Terminal : q
      Nonterminal : For
        Terminal : i
        Nonterminal : Expr ( 0 )
        Nonterminal : Expr ( q . Count - 1 )
        Nonterminal : Gate
          Terminal : H
          Nonterminal : IndexAccess ( q , i )
  Nonterminal : Operation
    Terminal : Main
    Nonterminal : Use ( reg , Qubit , 3 )
    Nonterminal : Gate                  ← 呼び出しも他のすべてと同じく Gate としてタグ付け
      Terminal : Prep
      Terminal : .
      Terminal : Fanout
      Nonterminal : Expr ( reg )
    Nonterminal : VarDecl
      Terminal : bit
      Terminal : r
      Nonterminal : Expr → Call ( M , IndexAccess ( reg , 0 ) )
この木は一度読まれた後、二度と触れられません 以降のすべてのステージはこの木ではなく IR 上で作動します。Prep.Fanout__sz3 のような名前はまだ存在しません — この下流で生まれます。

3Lower — AST からソース形 HIR へ（境界を越える）

in: エンジン AST + revision-bound session  ·  out: HirProgram (source-shaped HIR)  ·  パス: AstToHirLowering

ローワリングはエンジンの木を一度走査し、Qora が所有する不変 IR として組み直します。 HirProgram.Declarations が唯一の宣言所有ツリーです。 HirNamespaceDeclaration は下位宣言と open を所有し、 HirCallable はパラメータと HirBlock を所有します。 すべての文と式は、現在の revision の lowering session が発行した identity を持つ typed node になります。 例の IR: 

HirProgram
  Declarations[0] = HirNamespaceDeclaration("Prep")
    Declarations[0] = HirCallable("Fanout", Qubit q)
      HirForStatement(i, 0, n - 1)
        HirCallStatement(H, q[i])

  Declarations[1] = HirCallable("Main")
    HirQubitDeclarationStatement(reg, 3)
    HirCallStatement(Prep.Fanout, reg)
    HirVariableDeclarationStatement(bit r, HirMeasurementExpression(reg[0]))
なぜ木を型のあるデータとして組み直すのか? 後続のパスが文字列を再解析せずに、呼び出し先・引数・修飾子を検査できるからです。 ミドルエンド全体が IR ベースであるのも同じ理由です。パスが構造化されたノードを読み書きするので、 各パスは短く保たれ、間違えにくくなります。

4Expand & Resolve — インポートと呼び出し先 FQN

パス: ModuleLoader.Expand → Resolver.Resolve

Expand はモジュールローダです。ファイルに import "lib/prep.qor" があったなら、 このパスがそのファイルをパース・ローワリングし、最上位の宣言 subtree を 1 つの HirProgram に追加します。以降のすべては単一のプログラムを見ますが、 namespace の所有関係は名前文字列へ平坦化されず、宣言ツリーに残ります。 （例は何もインポートしないのでここでは何もしません。 ファイルが見つからない場合は QSEM020 になります。一方、循環する back-edge は loaded に登録済みのパスとしてエラーなしでスキップされます。QSEM021 は 廃止済みの予約コードとしてのみ残り、現在は出力されません。）

測定式は Expand と Resolve のあいだで target 形式の HIR へ書き換えません。 if (M(q[0]) == 1) は、条件内の canonical な HirMeasurementExpression のまま残ります。 その後、QoraMirLowering が測定を正確な評価位置へ配置し、short-circuit の制御フローを CFG で明示します。 最後に OpenQASM target lowering が構造化制御フローを復元し、必要な測定用 bit を出力します: 

operation Main() {
    use q = Qubit[2];
    if (M(q[0]) == 1) { X(q[1]); }
}
                       ↓ MIR lowering + OpenQASM target lowering
qubit[2] q;
int v0;
bit v1;
int v2;
int v3;
bit v4;
int v5;
v0 = 0;
v1 = measure q[v0];            ← 測定結果は SSA に対応する target value になる
v2 = 1;
v3 = int(v1);
v4 = v3 == v2;
if (v4) {
    v5 = 1;
    x q[v5];
}

続いて Resolve が演算定義と演算呼び出し先を完全修飾名（FQN）に変えます。 namespace Prep 内の演算 Fanout は Prep.Fanout になり、呼び出し側 Prep.Fanout(reg) がそれを指しているか確認されます。だから上の IR リスティングがすでに Fanout ではなく Prep.Fanout と読めるのです。ただし、このパスがすべての識別子を 解決するわけではありません。変数、ループ変数、キュービットのインデックス、条件式内の名前は、 次の検証段階でシンボルテーブルがスコープに基づいて確認します。呼び出し名が曖昧だった場合（open した 2 つの名前空間から見えた場合）は QSEM018、未知の名前空間やメンバは QSEM019 に なります。

5Validate — 意味のゲート

in: 解決済み IR  ·  out: エラーの一覧（またはなし）  ·  パス: QoraValidator + SymbolTableBuilder

検証は 1 つの問いに答えるパスです: このプログラムは OpenQASM が表現できる意味か? IR 全体を 一度走査し、すべての違反を集めます（最初のエラーで止まらない）。その結果は固いゲートです: エラーが 1 つでもあれば OpenQASM はまったく生成されません — だから壊れたプログラムが静かに 「成功したふり」をして誤った回路を返すことは決してありません。この段階で検証器は統合シンボルテーブルも作ります。 パラメータ、レジスタ、測定ビット、変数、定数、ループ変数がどのスコープに属するかを記録し、 各名前がどこで使われたかも集めます。すべての規則には安定したコード （QSEM001〜QSEM025）があり、エディタが波線を付けられます。そのいくつか:

コード拒否するもの
QSEM002ユーザ op への Controlled Foo（OpenQASM に def 用の ctrl @ はない）
QSEM006シグネチャに合わない引数の呼び出し — 個数、種類（量子ビット vs 角度）、またはレジスタサイズ
QSEM007未知のゲート/演算名（「もしかして …?」ヒント付き）
QSEM011再帰呼び出し（OpenQASM の def は再帰できない）
QSEM016レジスタ範囲を超えるリテラルの量子ビットインデックス
QSEM025スコープ内で解決できない識別子 — 未知の名前、または宣言前に使われた古典名
なぜ変換パスより先に検証するのか? 以降のすべてのパスが、プログラムはすでに健全だと仮定できるようになるからです。 単相化器はスコープで解決できない名前に出会わず、エミッタは不正な呼び出しに出会いません。 ゲートが全員の前に立っているからこそ、各変換パスは単純でいられます。

6Monomorphize — 量子ビット配列呼び出しの特殊化

in: 検証済み HIR  ·  out: 具体サイズの op を持つ HIR  ·  パス: Monomorphizer

表面型 Fanout(Qubit[] q) には配列長を書きません。単相化器（monomorphizer）は呼び出しごとに 実際のレジスタサイズを読み取り、具体的な内部コピーを打ち出し、パラメータへ既知の幅を 与えてから呼び出し先を書き換えます。共通 HIR は q.Count を保ち、target が後で既知の幅から lowering します。例の呼び出しは reg（量子ビット 3 個）を渡すので:

Prep.Fanout(Qubit[])  +  サイズ 3 のレジスタでの呼び出し  ⟶  Prep.Fanout__sz3(Qubit[3])

幅が具体的になったので、プログラムは二度目の検証を受けます。インデックス範囲と レジスタサイズの一致が照合する値を得て、このパスの後にはジェネリックな演算が残りません。

7Lower — ソース形 HIR から SSA/CFG MIR へ

in: 検証済み specialized HIR + 意味情報  ·  out: MirSnapshot  ·  パス: QoraMirLowering

HIR はユーザーが書いたプログラムの形を保つため、名前解決、型検査、診断に適しています。 それらの責務が終わると、QoraMirLowering が古典値を SSA version に分け、 分岐と反復を明示的な制御フローグラフに変換します。 

var x: int = 1;
x = x + 1;

↓ QoraMirLowering

v0 = constant 1
v1 = add v0, 1
return

結果は MirStage.Lowered の正確な不変 MirSnapshot オブジェクトです。 実際に消費した final HIR は LoweringSource に、MIR の source provenance は program-owned Origins に保持されます。Compilation identity は LoweringSource にだけあり、MIR へ複製されません。

8MIR 解析と内部逆演算の実体化

パス: exact MirProgram に対する analyses → MirAdjointMaterializer

制御フロー、effect、alias、memory state、path condition、control region の各解析は、 自分が説明する正確な MirProgram オブジェクトにだけ結び付けられます。 結果を HIR に複製せず、新しい program を持つ snapshot に以前の事実を再利用しません。

逆演算要求も MIR にだけ存在します。コンパイラ内部 scheduler が正確な MirQuantumApply に MirFunctor.Adjoint を付けると、 MirAdjointMaterializer が逆方向の MIR callable を合成し、要求を typed callable target へ書き換え、以前の snapshot を exact TransformationSource として持つ 新しい snapshot を発行します。 Qora ソースと HIR には Adjoint、逆演算マーカー、conjugation node がありません。 

MirQuantumApply(Target = Prepare, Functors = [MirFunctor.Adjoint])
                         ↓ MirAdjointMaterializer
MirCallable __qora_inverse_...(reversed unitary body)
MirQuantumApply(Target = __qora_inverse_..., Functors = [])
なぜこの境界を MIR に置くのか? Automatic uncomputation には SSA version、CFG path、storage state、正確な instruction identity が 必要です。要求と合成 callable を MIR に置けば、HIR にコンパイラ専用構文や別の target 経路を 追加せずに、scheduler と materializer が同じ根拠を共有できます。

9OpenQASM target lowering と出力

in: materialized MIR  ·  target: MirOpenQasmTargetProgram  ·  パス: MirOpenQasmLowering → MirQasmEmitter

OpenQASM backend は正確な materialized MIR snapshot を消費します。CFG から構造化された if、while、loop exit を復元し、SSA 値と phi edge を typed target の declaration と assignment に変え、衝突しない OpenQASM 名を決めます。結果の MirOpenQasmTargetProgram は target type、callable、declaration、statement と target-local identity を所有し、HIR を第二の正本として保持しません。

次に MirQasmEmitter が target model を直列化します。ソース名を再解決せず、 semantic fact を参照せず、逆演算や制御フローを組み立て直しません。将来の backend も HIR pipeline を 分岐させず、同じ canonical MIR を独自の typed lowering で消費できます。

この形は意図されたものです: エンジンとの境界 1 つ、続いて各自が IR に 1 つのことだけ をする小さなパスの一直線、そしてその前に立つ検証ゲートのおかげで、それ以降のすべてが単純でいられます。 言語機能を追加するのは、たいてい 1 つのパスを追加または拡張することであり — コンパイラを書き直すことではなく — 末尾の出力専用エミッタは、あなたが得る OpenQASM がパスの作った IR そのままであることを意味します。

この先が向かう場所 — 自動アンコンピュテーション Silq 流の自動アンコンピュテーション — 一時的な量子ビットがもう不要になる地点を見つけ、その逆演算を 自動的に注入する — ための境界は MIR にあります。Scheduler は exact MirProgram に結び付いた SSA/CFG facts を 消費して global cleanup order を求め、正確な MIR instruction に inverse request を注入します。 MirAdjointMaterializer と typed target path はすでにこの表現を消費します。条件、loop、 alias、classical witness stability、複数 ancilla の競合は、該当ケースを有効にする前に証明が必要です。

Source・AST・HIR・OpenQASM listing は実際の Qora コンパイラ （qora --json --stages）から得ており、短い MIR listing は実際の MIR type を使った説明用 sketch です。
