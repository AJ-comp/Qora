Qora Compilation Pipeline Design

The reference path from source text through source-shaped HIR, SSA/CFG MIR, a typed target, and OpenQASM emission

Qora is a small front end sitting on top of a parser engine (Janglim), plus a multi-pass middle end that Qora owns entirely. Compilation is a straight line of small, single-purpose passes: each takes the program in one form, does exactly one job, and hands the next pass a slightly more finished program — until the last pass prints OpenQASM 3. This document walks that line end to end, one stage at a time, combining compiler output with compact explanatory MIR sketches.

Source ─Parse─▶ AST ─Lower─▶ HIR ─Expand─▶ merged ─Desugar measure─▶ ─Resolve─▶ callee FQNs ─Validate + Symbols─▶ (STOP on error) ─Monomorphize─▶ specialized ─Lower MIR─▶ SSA/CFG MIR ─Analyze─▶ ─Materialize MIR-only inverses─▶ ─Target-lower─▶ typed OpenQASM model ─Emit─▶ OpenQASM 3

0The example — one file that touches every pass

To see the source-facing stages do real work, we use one small program that packs in a namespace, a qubit-array parameter (Qubit[]), and a call: 

namespace Prep {
    operation Fanout(q: Qubit[]) {        // the array length comes from each call site
        for i in 0..q.Count-1 { H(q[i]); }
    }
}

operation Main() {
    use reg = Qubit[3];
    Prep.Fanout(reg);                    // call across a namespace
    var r: bit = M(reg[0]);
}

Watch the name travel through the passes: Fanout gains a namespace (Prep.Fanout), gains a concrete size (Prep.Fanout__sz3), and finally flattens for OpenQASM (Prep_Fanout__sz3). Each change belongs to one pass below.

1Two worlds — where the engine stops and Qora begins

There is exactly one boundary in the whole compiler. Left of it lives the Janglim parser engine: it owns the grammar, the lexer, and turning text into a syntax tree. Right of it lives Qora: every pass that gives the program meaning, checks it, transforms it, and prints it. The two worlds meet at a single function — lowering — which reads the engine's tree once and never looks back.

Source → AST  │ engine (Janglim)
Qora │  HIR → SSA/CFG MIR → typed target → OpenQASM
Why keep the boundary this sharp? Everything Qora needs to reason about — types, inverses, generics, name safety — is done on Qora's own IR, not on the engine's tree. So the engine can stay a generic parser with no quantum knowledge, and Qora can add features (new passes) without ever touching the grammar. The one place that depends on the engine is lowering; the rest of the compiler would survive swapping the parser out.

2Parse — source to AST (the engine's job)

in: source text  ·  out: syntax tree  ·  owner: Janglim engine

The engine builds a lexer and an LALR parser from Qora's grammar, then turns the source into a parse tree. At this stage there is no meaning — Prep.Fanout is three tokens (Prep, ., Fanout), and a call and a gate look identical. The real tree for our example: 

Nonterminal : Program
  Nonterminal : Namespace
    Terminal : Prep
    Nonterminal : Operation
      Terminal : Fanout
      Nonterminal : Param
        Nonterminal : ArrayType
          Terminal : Qubit
        Terminal : q
      Nonterminal : For
        Terminal : i
        Nonterminal : Expr ( 0 )
        Nonterminal : Expr ( q . Count - 1 )
        Nonterminal : Gate
          Terminal : H
          Nonterminal : IndexAccess ( q , i )
  Nonterminal : Operation
    Terminal : Main
    Nonterminal : Use ( reg , Qubit , 3 )
    Nonterminal : Gate                  ← a call is tagged Gate, like everything else
      Terminal : Prep
      Terminal : .
      Terminal : Fanout
      Nonterminal : Expr ( reg )
    Nonterminal : VarDecl
      Terminal : bit
      Terminal : r
      Nonterminal : Expr → Call ( M , IndexAccess ( reg , 0 ) )
This tree is read once, then never touched again Every later stage works on the IR, not this tree. Nothing named Prep.Fanout__sz3 exists yet — it is born downstream.

3Lower — AST to source-shaped HIR (crossing the boundary)

in: engine AST + revision-bound session  ·  out: HirProgram (source-shaped HIR)  ·  pass: AstToHirLowering

Lowering walks the engine's tree once and rebuilds it as Qora's own immutable IR. HirProgram.Declarations is the authoritative containment tree: a HirNamespaceDeclaration owns nested declarations and open directives, while a HirCallable owns its parameters and HirBlock. Every statement and expression is a typed, identity-bearing node minted by the exact lowering session. The IR of our example: 

HirProgram
  Declarations[0] = HirNamespaceDeclaration("Prep")
    Declarations[0] = HirCallable("Fanout", Qubit q)
      HirForStatement(i, 0, n - 1)
        HirCallStatement(H, q[i])

  Declarations[1] = HirCallable("Main")
    HirQubitDeclarationStatement(reg, 3)
    HirCallStatement(Prep.Fanout, reg)
    HirVariableDeclarationStatement(bit r, HirMeasurementExpression(reg[0]))
Why rebuild the tree as typed data? Later passes can inspect call targets, arguments, and modifiers without re-parsing strings. This is the reason the whole middle end is IR-based: passes read and write structured nodes, so each one stays short and hard to get wrong.

4Expand & Resolve — imports and callee FQNs

passes: ModuleLoader.Expand → Resolver.Resolve

Expand is the module loader. If the file had import "lib/prep.qor", this pass parses that file, lowers it, and appends its top-level declaration subtrees to one HirProgram. Everything downstream sees one program, but namespace ownership remains structural rather than being flattened into copied name strings. (Our example imports nothing, so this is a no-op here. A missing file becomes QSEM020, while a cyclic back-edge reaches a path already registered in loaded and is skipped without an error. QSEM021 is retained only as a retired/reserved code and is no longer emitted.)

A measurement expression is not rewritten into target-shaped HIR between expansion and resolution. if (M(q[0]) == 1) remains a canonical HirMeasurementExpression inside the condition. Later, QoraMirLowering places the measurement at its exact evaluation point and represents short-circuit control flow explicitly in the CFG. OpenQASM target lowering then recovers structured control flow and emits the required measured bit: 

operation Main() {
    use q = Qubit[2];
    if (M(q[0]) == 1) { X(q[1]); }
}
                       ↓ MIR lowering + OpenQASM target lowering
qubit[2] q;
int v0;
bit v1;
int v2;
int v3;
bit v4;
int v5;
v0 = 0;
v1 = measure q[v0];            ← the measurement result is now an SSA-backed target value
v2 = 1;
v3 = int(v1);
v4 = v3 == v2;
if (v4) {
    v5 = 1;
    x q[v5];
}

Resolve then turns operation definitions and operation call targets into fully-qualified names (FQNs). Inside namespace Prep, the operation Fanout becomes Prep.Fanout, and the call site Prep.Fanout(reg) is checked to point at it. This is why the HIR listing above already reads Prep.Fanout, not Fanout. This pass does not resolve every identifier in the program. Variables, loop variables, qubit indices, and names inside conditions are checked by the symbol table during validation. If a call target were ambiguous (visible from two opened namespaces) it would be QSEM018; an unknown namespace or member is QSEM019.

5Validate — the semantic gate

in: resolved IR  ·  out: a list of errors (or none)  ·  pass: QoraValidator + SymbolTableBuilder

Validation is the pass that answers one question: does this program mean something OpenQASM can express? It walks the whole IR once and collects every violation (no stopping at the first). The result is a hard gate: one error and no OpenQASM is produced at all, so a broken program can never quietly "succeed" and hand back a wrong circuit. During this pass the validator also builds the unified symbol table: parameters, registers, measurement bits, variables, constants, and loop variables are placed into scopes, and each use site is recorded. Every rule has a stable code (QSEM001–QSEM025) so the editor can attach a squiggle. A few of them:

CodeRejects
QSEM002Controlled Foo on a user op (OpenQASM has no ctrl @ for a def)
QSEM006a call whose arguments do not match the signature — count, kind (qubit vs angle), or register size
QSEM007an unknown gate or operation name (with a "did you mean …?" hint)
QSEM011recursive calls (OpenQASM defs cannot recurse)
QSEM016a literal qubit index outside its register's range
QSEM025an identifier that does not resolve in scope — an unknown name or a classical name used before declaration
Why validate before the transforming passes? Because it lets every later pass assume the program is already sound. The monomorphizer never meets a name that failed scope resolution, and the emitter never meets a bad call. Each transforming pass gets to be simple because the gate stands in front of them all.

6Monomorphize — specializing qubit-array calls

in: validated HIR  ·  out: HIR with concrete-size ops  ·  pass: Monomorphizer

The surface type Fanout(q: Qubit[]) deliberately omits the array length. At each call site, the monomorphizer reads the actual register size, stamps out a concrete internal copy, gives its parameter that known width, and rewrites the call to point at the copy. Common HIR preserves q.Count; the target later lowers it from the known width. Our call passes reg (3 qubits), so:

Prep.Fanout(Qubit[])  +  call with a size-3 register  ⟶  Prep.Fanout__sz3(Qubit[3])

Because sizes are now concrete, the program is validated a second time: checks that only need a known register width — index bounds and register-size matches — finally have something to run against. After this pass, no generic operations remain.

7Lower — source-shaped HIR to SSA/CFG MIR

in: accepted specialized HIR + semantic facts  ·  out: MirSnapshot  ·  pass: QoraMirLowering

HIR still resembles the program the user wrote, which makes name resolution, type checking, and diagnostics straightforward. After those responsibilities are complete, QoraMirLowering creates the compiler's execution-oriented form: classical values become SSA versions and branches and loops become an explicit control-flow graph. 

var x: int = 1;
x = x + 1;

↓ QoraMirLowering

v0 = constant 1
v1 = add v0, 1
return

The result is one immutable, revision-qualified MirSnapshot. Its origin table and typed cross-stage links connect every MIR callable, value, storage object, and qubit resource to its HIR source or explicitly classify it as a compiler temporary. A backend therefore never has to guess which source declaration a MIR identity came from.

8Analyze MIR and materialize internal inverses

passes: revision-bound MIR analyses → MirAdjointMaterializer

Control-flow, effect, alias, memory-state, path-condition, and control-region analyses all consume the exact MIR revision they describe. Their results are not copied into HIR and cannot be reused against a changed graph.

Inverse requests also belong exclusively to MIR. A compiler-internal scheduler may mark one exact MirQuantumApply with MirFunctor.Adjoint. The MirAdjointMaterializer then synthesizes the required inverse MIR callable, rewrites the request to a typed callable target, and publishes a new snapshot with an exact parent and rebased origins. Qora source and HIR contain no Adjoint, inverse marker, or conjugation node. 

MirQuantumApply(Target = Prepare, Functors = [MirFunctor.Adjoint])
                         ↓ MirAdjointMaterializer
MirCallable __qora_inverse_...(reversed unitary body)
MirQuantumApply(Target = __qora_inverse_..., Functors = [])
Why is this boundary in MIR? Automatic uncomputation needs SSA versions, CFG paths, storage states, and exact instruction identities. Keeping requests and synthesized callables in MIR lets the scheduler and materializer share that evidence without adding compiler-only syntax to HIR or creating a second target path.

9Target-lower and emit OpenQASM 3

in: materialized MIR  ·  target: MirOpenQasmTargetProgram  ·  passes: MirOpenQasmLowering → MirQasmEmitter

The OpenQASM backend consumes the exact materialized MIR snapshot. It recovers structured if, while, and loop exits from the CFG, converts SSA values and phi edges into typed target declarations and assignments, and assigns collision-free OpenQASM names. The resulting MirOpenQasmTargetProgram owns target types, callables, declarations, statements, and their target-local identities; it does not carry HIR as a second source of truth.

MirQasmEmitter then serializes that target model. It does not resolve source names, inspect semantic facts, synthesize inverses, or reconstruct control flow. A future backend can consume the same canonical MIR through its own typed lowering without forking the HIR pipeline.

The shape is deliberate: one boundary with the engine, then a line of small passes that each do one thing to the IR, with a validation gate up front so everything after it can be simple. Adding a language feature usually means adding or extending one pass — not rewriting the compiler — and the print-only emitter at the end means the OpenQASM you get is exactly the IR the passes built.

Where this is heading — automatic uncomputation Silq-style automatic uncomputation — finding where a temporary qubit is no longer needed and injecting its inverse automatically — now has the correct stage boundary. The scheduler will consume revision-bound SSA/CFG facts, find a global cleanup order, and inject exact MIR instruction requests. MirAdjointMaterializer and the typed target path already consume that representation. Conditions, loops, aliases, classical-witness stability, and conflicts between several ancillas still need explicit proofs before the scheduler can enable those cases.
