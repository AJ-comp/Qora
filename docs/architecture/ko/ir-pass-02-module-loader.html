2. SourceGraphLoader와 ModuleLoader

문서 그래프 준비와 순수 HIR 병합의 책임 경계

← 1. QoraLowering 패스 목차 3. MeasureConditionLowering →

import 확장은 두 단계로 나뉩니다.
먼저 SourceGraphLoader가 파일 I/O와 문서별 구문 분석·lowering을 한 번씩 수행하고, 불변 SourceSetSnapshot과 내부 LoadedSourceGraph를 준비합니다.
구문 분석 중 만들어진 Janglim AST는 내부 SyntaxParseProduct에서 즉시 lowering할 때만 사용하며, 공개 소스 스냅샷에는 Qora 소유의 불변 구문 투영만 남습니다.
그 뒤 ModuleLoader는 준비된 문서 그래프만 읽어 하나의 QProgram과 imported-node introduction 목록을 만들며, 파일을 열거나 텍스트를 다시 파싱하지 않습니다.

1. SourceGraphLoader가 준비하는 값

SourceGraphLoader.Load는 진입 텍스트와 CompilationOptions, 그리고 현재 CompilationId·CompilationRevision을 받습니다.
먼저 진입 문서를 등록하고, 각 import를 발견할 때마다 문서를 한 번만 읽어 독립된 스냅샷으로 보존합니다.

1. 문서 identity 발급

SourceDocumentRef에 컴파일 identity, revision, 문서 Id를 함께 넣습니다.
따라서 서로 다른 재컴파일의 같은 경로도 같은 문서 위치로 혼동되지 않습니다.

2. 문서별 구문 스냅샷

QoraParser.ParseOnCurrentThread가 내부 SyntaxParseProduct를 만들고, 그 안의 Snapshot에는 토큰·Qora 소유의 불변 파스 트리와 AST 투영·캡처된 문자열·구문 진단만 넣습니다.
변경 가능한 LoweringAst는 이 내부 산출물에만 있으며 SourceSetSnapshot에는 들어가지 않습니다.

3. 문서별 lowering

구문 분석에 성공하고 임시 AST가 있으면 QoraLowering.Lower(parseProduct.LoweringAst, documentRef)를 즉시 호출합니다.
생성된 모든 위치는 해당 문서를 가리키는 SourceSpan이며, lowering 뒤에는 parser-owned AST를 장기 아티팩트로 보관하지 않습니다.

4. import 그래프 고정

해결된 간선과 해결하지 못한 간선을 모두 ImportGraph에 남깁니다.
해결하지 못한 간선은 Imported = null이지만 원문 target과 지시문 위치를 보존합니다.

경로 중복, 순환, diamond

canonical path로 이미 등록된 문서를 다시 만나면 새 문서를 만들지 않고 기존 SourceDocumentRef를 간선의 대상으로 사용합니다.
새 문서는 하위 import를 순회하기 전에 등록되므로 순환 back-edge도 같은 문서 identity로 닫히며, diamond 그래프의 공유 문서도 한 번만 읽고 파싱합니다.
경로 비교는 Windows에서 대소문자를 무시하고, 그 밖의 운영체제에서는 ordinal 비교를 사용합니다.

오류도 그래프의 일부입니다 import를 해석할 기준 디렉터리가 없거나 경로가 유효하지 않거나 문서를 읽을 수 없으면 QSEM020을 수집합니다.
이때 시도한 import 간선과 지시문 SourceSpan은 버리지 않으므로, 도구가 실패한 관계까지 조회할 수 있습니다.

2. ModuleLoader의 순수 병합

ModuleLoader.Expand의 유일한 입력은 LoadedSourceGraph입니다.
진입 문서의 QProgram이 없으면 병합할 구조 자체가 없으므로 호출 계약 위반으로 처리하며, 정상 입력에서는 아래 순서로 병합합니다. 

operations = entry.Operations
opens      = entry.Opens
visited    = { Sources.Entry }

MergeImports(importer):
  for edge in Sources.Imports.Outgoing(importer):
    if edge.Imported is null or already visited:
      continue
    mark imported as visited
    MergeImports(imported)
    if imported is not in LoweredDocuments:
      continue
    operations += LoweredDocuments[imported].Operations
    introductions += every imported HIR node except its QProgram root
    merge opens by namespace

return ModuleLoader.Result(
  Program = entry with {
    Operations = operations,
    Opens = distinct open targets per namespace,
    Imports = null
  },
  Introductions = introductions
)

연산 순서는 진입 문서가 항상 먼저이며, import 하위 트리는 깊이 우선 후위 순서로 이어집니다.
예를 들어 main → A → C와 main → B → C인 diamond에서는 main의 연산 뒤에 C, A, B의 연산이 한 번씩 추가됩니다.
이 순서는 ImportGraph.Outgoing의 소스 순서와 SourceDocumentRef 기반 방문 집합으로 결정됩니다.

병합하면서 처음 들어온 imported HIR node는 부모 HIR의 복사본이 아니므로 NodeDerivation으로 기록하지 않습니다.
대신 HirNodeIntroduction(IntroducedNodeId, Document, ImportedDocument)으로 분류하고, HirPipelineBuilder가 Lowered → ImportsExpanded 전이에 함께 전달합니다.
따라서 HirLineage는 새 node를 identity copy, compiler synthesis, source introduction 가운데 정확히 하나로 설명할 수 있습니다.

또한 IDE가 문서별 구문 상태와 import 관계를 그대로 조회할 수 있고, 미래의 증분 컴파일도 문서 그래프 invalidation과 HIR 병합을 별도 경계에서 발전시킬 수 있습니다.

3. SourceSpan과 문서별 위치

SourceSpan은 Document, Start, End를 담는 반열림 문자 범위입니다.
여기서 Document는 단순 경로나 로컬 정수가 아니라 CompilationId·CompilationRevision·SourceDocumentId를 포함한 SourceDocumentRef입니다.
따라서 import 문서의 HIR 노드도 위치를 버리지 않으며, 다른 문서나 이전 revision의 같은 offset과 섞이지 않습니다.

4. 실패와 부분 아티팩트

진입 문서의 구문 분석이 실패하면 문서별 SyntaxSnapshot만 남고 HIR은 시작되지 않습니다.
구문 진단은 없지만 entry QProgram이 만들어지지 않은 빈 소스도 HirPreflight의 QSEM040으로 중단하며, 이때 ModuleLoader는 호출되지 않습니다.
반면에 진입 문서가 lowering되었지만 import 문서의 구문 분석이나 경로 해석이 실패하면, 컴파일러는 Lowered와 ImportsExpanded HIR milestone을 보존한 뒤 중단합니다.
이후 MeasureConditionLowering·이름 해소·검증·MIR·대상 backend는 실행하지 않습니다.
