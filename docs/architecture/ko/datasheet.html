Qora 컴파일러 데이터시트

Compilation · SourceSet · HIR semantics · MIR · cross-stage links · target artifacts

전체 구조 패스 목차 SourceSet HIR MIR 단계 링크 Targets 진단·불변 조건

Qora의 공개 컴파일 결과는 한 source revision을 나타내는 불변 Compilation입니다.
CompilationSession이 한 논리 컴파일의 identity와 branch-safe revision 발급을 소유하고, 각 결과는 자신의 Revision과 선택적 ParentRevision을 기록합니다.
이 aggregate가 Sources, Hir, 요청된 경우의 Mir, Links, Targets, Diagnostics를 소유하며, 각 단계의 사실은 자신이 설명하는 정확한 snapshot identity로 한정됩니다.
따라서 HIR 트리와 다른 세대의 의미 모델을 우연히 결합하거나, backend가 원본 의미 정보를 덮어쓰는 구조를 허용하지 않습니다.

1. 권위 있는 전체 구조

Sources

원문과 구문을 소유합니다.
HIR·의미 사실·backend 이름을 흡수하지 않습니다.

Hir

구조 세대, semantic artifact, HirLineage를 함께 소유합니다.
Links.Hir는 같은 lineage의 aggregate 편의 뷰입니다.

Mir

typed SSA/CFG 구조, origin, 구조 인덱스, 분석 cache를 한 snapshot에 묶습니다.
동일한 callable-local 정수 Id는 composite reference로 구분합니다.

Targets

backend별 최종 아티팩트를 맵으로 소유합니다.
대상 전용 이름·타입·합성 사실은 원본 HIR로 역류하지 않습니다.

세션, revision, 요청 산출물

Compilation.ParentRevision선형 순서와 별개로 실제 재컴파일 부모를 기록하므로 sibling revision의 분기 관계를 잃지 않음

예를 들어 revision 0에서 두 번 재컴파일하면 두 결과의 ParentRevision은 모두 0이지만 세션이 revision 1과 2를 각각 발급합니다.
따라서 revision을 단순히 parent + 1로 계산할 때 생기는 sibling 충돌이 없으며, 이전 Compilation도 변경되지 않습니다.

3. SourceSet과 문서 그래프

Compilation.Sources는 한 revision에 입력된 모든 문서를 독립적으로 보존합니다.
각 SourceDocumentSnapshot은 SourceDocumentRef, 텍스트, 선택적 경로를 소유하며, SyntaxByDocument는 각 문서에 정확히 하나의 SyntaxSnapshot을 연결합니다.
각 구문 스냅샷은 parser-engine 객체가 아니라 Qora 소유의 불변 트리 투영과 캡처된 문자열을 담으므로, import 문서는 통합 HIR에 병합된 뒤에도 외부 AST 변경에 흔들리지 않는 구문 정보를 문서 단위로 조회할 수 있습니다.

타입담는 값identity
SourceSetSnapshotentry, 모든 문서, 문서별 syntax, ImportGraphCompilationId + CompilationRevision
SourceDocumentSnapshot정확한 텍스트와 선택적 canonical/original pathSourceDocumentRef
SyntaxSnapshot토큰, Qora 소유의 불변 파스 트리·AST 투영, 캡처된 문자열, 구문 진단소유 문서의 SourceDocumentRef
SyntaxParseProductsnapshot과 Janglim LoweringAst를 잠시 묶는 내부 파싱 산출물공개·저장 대상이 아니며 문서별 lowering 뒤 폐기

공개 QoraParser.Parse도 구문 전용 API이며, 단일 문서를 revision 0의 독립된 syntax snapshot으로 반환합니다.
whole-program 결과가 필요하면 QoraCompiler.Compile을 사용해야 하며, parser 결과에 HIR이나 target을 덧붙이거나 mutable LoweringAst를 꺼내는 방식은 지원하지 않습니다.

4. HIR 구조와 semantic artifact

HirSnapshot은 한 세대의 HirProgram 선언 트리, 부모 snapshot Id, 구조 인덱스, node Id 기반 source map을 소유합니다.
이 객체에는 의미 모델을 넣지 않으며, 의미 사실은 HirSemanticArtifactId(Source, Phase)로 식별되는 별도 HirSemanticArtifact가 소유합니다.
validation artifact는 모델과 함께 HirValidationOutcome을 소유하며, 그 outcome의 Status와 불변 Diagnostics가 accepted/rejected 판단의 유일한 권위입니다.
HirCompilation은 이 구조 세대와 의미 산출물뿐 아니라 같은 snapshot 객체 집합을 사용하는 HirLineage도 직접 소유하므로, 계보와 HIR history가 서로 분리된 권위 저장소로 어긋날 수 없습니다.
결과적으로 분석을 추가해도 기존 HIR tree snapshot은 변경되지 않습니다.

조회반환 값의미

Hir.MilestonesHirStage → HirSnapshotrewrite가 없으면 여러 stage가 같은 snapshot을 가리킬 수 있음
Hir.Lineage부모 세대, identity derivation, synthesis provenance, source introduction정확히 같은 HirSnapshot 객체 집합에 결합

HIR milestone의 정식 순서는 Lowered → ImportsExpanded → Resolved → Specialized입니다.
Adjoint와 conjugation은 사용자 문법과 HIR에 존재하지 않으며, 내부 역연산 처리 단계는 MIR의 Lowered → InverseRequestsInjected → AdjointsMaterialized 순서로 관리합니다.
실제 rewrite가 없을 때 뒤 milestone이 앞 snapshot을 alias할 수는 있지만, 뒤 단계가 앞 단계보다 오래된 revision을 가리킬 수는 없습니다.

의미 모델과 typed HIR 계보

HirSemanticModel은 자신이 분석한 exact HIR의 scope graph와 의미 사실만 담습니다.
HirSemanticArtifact.Diagnostics는 자신이 소유한 ValidationOutcome.Diagnostics의 뷰이며, CompilationDiagnostic은 여기에 stage와 origin을 붙여 투영할 뿐 별도의 validation 결과를 유지하지 않습니다.
effect-analysis artifact는 같은 snapshot의 exact accepted validation artifact를 ValidationBasis로 명시하고 동일한 validation outcome을 공유합니다.
후속 구조 패스의 관계는 HirCompilation.Lineage가 소유하고, Compilation.Links.Hir는 그 exact instance를 다시 노출합니다.
HirSemanticContext는 owner HirCompilation에 실제로 들어 있는 current snapshot과 semantic artifact 객체만 받으며, semantic identity를 보존하는 경로를 통해서만 node Id를 분석 기준 snapshot으로 변환합니다.
따라서 copy lineage와 의미 사실이 하나의 mutable bag에서 서로 drift하지 않으며, 새 임시 선언을 원본 제어문의 symbol로 잘못 해석하지 않습니다.

전이 분류뜻허용 질의

암시적 동일 Id부모에도 같은 Id·kind·소유 operation이 존재하는 보존 node별도 edge 없이 부모로 이동

첫 HIR snapshot을 제외한 모든 node는 부모에 동일 identity로 이미 존재하거나, 위 세 명시 분류 가운데 정확히 하나를 가져야 합니다.
이 totality 검사가 누락된 origin과 이중 분류를 publication 시점에 거부합니다.

장기 확장 경계 사용자 정의 타입·클래스·필드·메서드·상속·인터페이스·제네릭·오버로드가 추가되어도 선언 관계는 typed scope/symbol graph를 확장하는 방향으로 유지합니다.
namespace containment, import edge, 미래의 base-type/interface edge를 하나의 문자열 맵이나 mutable 전역 표로 합치지 않습니다.

5. MIR snapshot과 분석 저장소

Compilation.Mir는 컴파일이 MIR lowering까지 도달했을 때만 존재하는 MirSnapshot입니다.
이 snapshot은 MirSnapshotId, MirStage, 선택적 exact Parent, lowering 원본 HirSnapshotId, lowering profile, typed SSA/CFG 프로그램, origin table, 구조 인덱스, cross-stage links, 분석 저장소를 함께 소유합니다.
HIR lowering이 root Lowered snapshot을 만들고, inverse request 주입과 materialization은 각각 더 높은 revision의 새 snapshot을 발행하므로 Compilation.Mir은 요청한 pipeline이 끝낸 최종 MIR을 가리킵니다.
생성 시 verifier를 통과해야 하므로 downstream 분석은 검증된 구조만 받습니다.

HIR의 EffectAnalysis와 MIR의 Mir.Analyses.Effects는 같은 이름의 중복 결과가 아닙니다.
전자는 source-shaped HIR에서 자동 uncomputation 판단에 필요한 semantic event와 summary를 만들고, 후자는 SSA/CFG에서 실행 경로와 storage 상태를 포함한 MIR 수준 사실을 만듭니다.

6. 단계 간 링크와 source map

각 IR은 자신의 구조와 자기 단계 내부의 관계를 소유하며, Compilation.Links는 단계 간 질의를 위한 exact 공유 뷰를 제공합니다.
HIR 내부 계보의 권위 소유자는 HirCompilation.Lineage이고 Links.Hir는 같은 instance이며, Links.Mir는 MIR이 lowering된 exact HIR snapshot과 symbol semantic artifact를 명시합니다.
MIR callable은 HIR callable node와 symbol에서 찾을 수 있는 typed 참조로 연결됩니다.
반면에 HIR symbol과 MIR value·storage·qubit의 관계는 양쪽에서 조회할 수 있는 typed many-to-many 맵이며, 별도의 total disposition map이 링크가 없는 경우도 의도적인 non-lowering 또는 compiler temporary로 설명합니다.

7. target artifact backend map

Compilation.Targets는 TargetArtifactSet이며, 내부 권위 저장소는 TargetBackend → ITargetArtifact 불변 맵입니다.
현재 backend key는 OpenQasm 하나이지만, 소비자는 필요하면 Find(TargetBackend)를 사용하고 기존 편의 속성 Targets.OpenQasm도 사용할 수 있습니다.
공통 ITargetArtifact 계약은 Backend만 요구하므로, 앞으로 여러 backend가 서로 다른 원본 IR을 소비하더라도 하나의 nullable target 필드나 공용 mutable 상태를 공유하지 않습니다.

현재 QasmBackend.Run은 exact materialized MirSnapshot만 소비하며, HIR이나 HIR semantic model을 다시 조회하지 않습니다.
backend는 MirOpenQasmLowering으로 MirOpenQasmTargetProgram을 만들고, OpenQasmArtifact가 target model을 소유한 뒤 MirQasmEmitter.Emit(Program)으로 Text를 파생합니다.
따라서 target text는 독립적으로 저장된 또 하나의 권위 입력이 아니라 target model의 직렬화 결과입니다.

따라서 backend가 source-shaped HIR을 별도 분기로 다시 해석하지 않고, MIR 분석과 target lowering 사이에도 하나의 권위 경로만 남습니다.
또한 bit-register의 unsigned cast는 target lowering 뒤에 명시적 MirQasmUnsignedCastExpression이 되므로, 문자열 이름 예외가 callable lookup이나 call graph에 유입되지 않습니다.

8. 진단, 실패, 재컴파일

CompilationDiagnostic은 CompilationStage, 원래 QoraError, typed DiagnosticOrigin을 함께 보존합니다.
origin은 Source, Hir, Mir, Target 가운데 하나이며, 각 variant가 자기 단계에 맞는 identity를 요구합니다.
특히 target 진단은 DiagnosticOrigin.Target(Backend, TargetDiagnosticInput)을 사용하고, 입력 union은 exact Hir(snapshot) 또는 Mir(snapshot, optional location)입니다.
진단이 하나라도 있으면 Compilation.Succeeded는 false이고 성공한 target artifact는 존재하지 않지만, 실패 전에 완성된 source·HIR·semantic·MIR 아티팩트는 그대로 조회할 수 있습니다.
반면에 성공한 결과는 CompilationOutputPlan의 MIR 여부와 target 집합을 정확히 충족해야 하며, 요청하지 않은 결과를 관성적으로 생성하지 않습니다.

QoraCompiler.Compile은 새 CompilationSession에서 root revision을 만들고, QoraCompiler.Recompile은 이전 결과가 속한 같은 세션에 다음 revision을 요청합니다.
각 자식은 실제 부모를 ParentRevision으로 기록하므로, 같은 부모에서 분기해도 revision identity와 ancestry가 모두 보존됩니다.
이전 snapshot은 변경되지 않으며, source·HIR·MIR identity가 revision을 포함하므로 새 결과와 섞이지 않습니다.
다만 문서 의존성 기반 invalidation, snapshot 재사용, 별도 컴파일은 아직 구현되지 않았으며 현재 구조가 이를 위한 경계만 제공합니다.
