Qora 컴파일 파이프라인 설계

소스가 source-shaped HIR, SSA/CFG MIR, typed target, OpenQASM 방출까지 지나가는 기준 흐름

Qora는 파서 엔진(Janglim) 위에 얹힌 얇은 프런트엔드와, 그 위에 Qora가 전적으로 소유하는 멀티패스 미들엔드로 이루어져 있습니다. 컴파일은 작고 단일 목적을 가진 패스들의 일직선입니다. 각 패스는 한 형태의 프로그램을 받아 딱 한 가지 일만 하고, 조금 더 완성된 프로그램을 다음 패스에 넘깁니다 — 마지막 패스가 OpenQASM 3을 출력할 때까지요.
이 문서는 그 일직선을 처음부터 끝까지 한 단계씩 따라가면서, 실제 compiler output과 설명을 위한 짧은 MIR 도식을 함께 사용해요.

0예제 — 모든 패스를 건드리는 파일 하나

사용자 소스를 처리하는 단계가 실제로 일하는 모습을 보기 위해, 네임스페이스와 큐비트 배열 파라미터(Qubit[]), 호출을 한 프로그램에 담았습니다: 

namespace Prep {
    operation Fanout(q: Qubit[]) {        // 배열 길이는 호출부마다 정해짐
        for i in 0..q.Count-1 { H(q[i]); }
    }
}

operation Main() {
    use reg = Qubit[3];
    Prep.Fanout(reg);                    // 네임스페이스를 넘나드는 호출
    var r: bit = M(reg[0]);
}

이름이 패스들을 지나며 어떻게 변하는지 보세요. Fanout은 네임스페이스를 얻고 (Prep.Fanout), 구체적 크기를 얻은 뒤(Prep.Fanout__sz3), 마지막으로 OpenQASM용으로 평탄화됩니다(Prep_Fanout__sz3). 각 변화는 바로 아래의 한 패스가 맡습니다.

1두 세계 — 엔진이 멈추고 Qora가 시작되는 곳

컴파일러 전체에 경계는 정확히 하나뿐입니다. 왼쪽에는 Janglim 파서 엔진이 있습니다 — 문법·렉서, 그리고 텍스트를 구문 트리로 바꾸는 일을 소유합니다. 오른쪽에는 Qora가 있습니다 — 프로그램에 의미를 부여하고, 검사하고, 변환하고, 출력하는 모든 패스가 여기 있습니다. 두 세계는 함수 하나에서 만납니다 — 로워링(lowering) — 이 함수는 엔진의 트리를 딱 한 번 읽고 다시는 돌아보지 않습니다.

소스 → AST  │ 엔진 (Janglim)
Qora │  HIR → SSA/CFG MIR → typed target → OpenQASM
왜 경계를 이렇게 뚜렷이 유지하나? Qora가 다뤄야 할 모든 것 — 타입, 역연산, 제네릭, 이름 안전성 — 은 엔진의 트리가 아니라 Qora 자신의 IR 위에서 처리됩니다. 그래서 엔진은 양자에 대해 아무것도 모르는 범용 파서로 남을 수 있고, Qora는 문법을 건드리지 않고도 기능(새 패스)을 추가할 수 있습니다. 엔진에 의존하는 유일한 지점은 로워링이며, 나머지 컴파일러는 파서를 통째로 교체해도 살아남습니다.

2Parse — 소스에서 AST로 (엔진의 몫)

in: 소스 텍스트  ·  out: 구문 트리  ·  담당: Janglim 엔진

엔진은 Qora 문법으로부터 렉서와 LALR 파서를 만든 뒤, 소스를 파스 트리로 바꿉니다. 이 단계에는 아무 의미가 없습니다 — Prep.Fanout은 토큰 세 개 (Prep, ., Fanout)이며, 호출과 게이트는 똑같이 생겼습니다. 예제의 실제 트리: 

Nonterminal : Program
  Nonterminal : Namespace
    Terminal : Prep
    Nonterminal : Operation
      Terminal : Fanout
      Nonterminal : Param
        Nonterminal : ArrayType
          Terminal : Qubit
        Terminal : q
      Nonterminal : For
        Terminal : i
        Nonterminal : Expr ( 0 )
        Nonterminal : Expr ( q . Count - 1 )
        Nonterminal : Gate
          Terminal : H
          Nonterminal : IndexAccess ( q , i )
  Nonterminal : Operation
    Terminal : Main
    Nonterminal : Use ( reg , Qubit , 3 )
    Nonterminal : Gate                  ← 호출도 다른 모든 것처럼 Gate로 태깅됨
      Terminal : Prep
      Terminal : .
      Terminal : Fanout
      Nonterminal : Expr ( reg )
    Nonterminal : VarDecl
      Terminal : bit
      Terminal : r
      Nonterminal : Expr → Call ( M , IndexAccess ( reg , 0 ) )
이 트리는 한 번 읽힌 뒤 다시는 손대지 않습니다 이후 모든 단계는 이 트리가 아니라 IR 위에서 작동합니다. Prep.Fanout__sz3 같은 이름은 아직 존재하지 않습니다 — 이 뒤에서 태어납니다.

3Lower — AST에서 소스 모양 HIR로 (경계를 넘다)

in: 엔진 AST + revision-bound session  ·  out: HirProgram (source-shaped HIR)  ·  패스: AstToHirLowering

로워링은 엔진의 트리를 한 번 순회하며 Qora가 소유하는 불변 IR로 다시 세워요.
HirProgram.Declarations가 유일한 선언 소유 트리이며, HirNamespaceDeclaration은 하위 선언과 open을 소유하고 HirCallable은 매개변수와 HirBlock을 소유해요.
그리고 모든 문장과 표현식은 현재 revision의 lowering session이 발급한 identity를 가진 typed node가 돼요. 예제의 IR은 다음과 같아요. 

HirProgram
  Declarations[0] = HirNamespaceDeclaration("Prep")
    Declarations[0] = HirCallable("Fanout", Qubit q)
      HirForStatement(i, 0, n - 1)
        HirCallStatement(H, q[i])

  Declarations[1] = HirCallable("Main")
    HirQubitDeclarationStatement(reg, 3)
    HirCallStatement(Prep.Fanout, reg)
    HirVariableDeclarationStatement(bit r, HirMeasurementExpression(reg[0]))
왜 트리를 타입 있는 데이터로 다시 만드나? 이후 패스가 문자열을 다시 파싱하지 않고 호출 대상·인수·수식자를 검사할 수 있기 때문입니다. 미들엔드 전체가 IR 기반인 것도 같은 이유입니다. 패스들이 구조화된 노드를 읽고 쓰므로, 각 패스는 짧게 유지되고 틀리기 어렵습니다.

4Expand & Resolve — 임포트와 호출 대상 FQN

패스: ModuleLoader.Expand → Resolver.Resolve

Expand는 모듈 로더입니다. 파일에 import "lib/prep.qor"가 있었다면, 이 패스가 그 파일을 파싱·로워링하고 최상위 선언 subtree를 하나의 HirProgram에 이어 붙여요.
이후 모든 단계는 하나의 프로그램을 보지만, namespace 소유 관계는 이름 문자열로 평탄화되지 않고 선언 트리에 그대로 남아요. (예제는 아무것도 임포트하지 않으므로 여기서는 아무 일도 하지 않아요.
파일이 없으면 QSEM020이 됩니다. 반면에 순환 back-edge는 loaded에 이미 등록된 경로로 보아 오류 없이 생략해요.
QSEM021은 폐기된 예약 코드로만 남아 더 이상 생성하지 않아요.)

측정식은 Expand와 Resolve 사이에서 target 모양의 HIR로 바꾸지 않아요. if (M(q[0]) == 1)은 조건 안의 canonical HirMeasurementExpression으로 그대로 남아요. 이후 QoraMirLowering이 측정을 정확한 평가 위치에 놓고, short-circuit 제어 흐름을 CFG로 분명하게 표현해요. 마지막으로 OpenQASM target lowering이 구조화된 제어 흐름을 복원하면서 필요한 측정용 bit을 방출해요: 

operation Main() {
    use q = Qubit[2];
    if (M(q[0]) == 1) { X(q[1]); }
}
                       ↓ MIR lowering + OpenQASM target lowering
qubit[2] q;
int v0;
bit v1;
int v2;
int v3;
bit v4;
int v5;
v0 = 0;
v1 = measure q[v0];            ← 측정 결과가 SSA에 대응하는 target value가 돼요
v2 = 1;
v3 = int(v1);
v4 = v3 == v2;
if (v4) {
    v5 = 1;
    x q[v5];
}

이어 Resolve가 연산 정의와 연산 호출 대상을 정규화된 이름(FQN)으로 바꿉니다. namespace Prep 안의 연산 Fanout은 Prep.Fanout이 되고, 호출부 Prep.Fanout(reg)가 그것을 가리키는지 확인됩니다. 그래서 위 HIR 리스팅이 이미 Fanout이 아니라 Prep.Fanout으로 읽히는 것입니다. 다만 여기서 모든 식별자를 처리하는 것은 아닙니다. 변수, 루프 변수, 큐비트 인덱스, 조건식 안의 이름은 다음 검증 단계의 심볼 테이블이 스코프 기준으로 확인합니다. 어떤 호출 이름이 모호했다면(open된 두 네임스페이스에서 보였다면) QSEM018이 되고, 알 수 없는 네임스페이스나 멤버는 QSEM019가 됩니다.

5Validate — 의미 게이트

in: 해소된 IR  ·  out: 오류 목록 (또는 없음)  ·  패스: QoraValidator + SymbolTableBuilder

검증은 한 가지 질문에 답하는 패스입니다: 이 프로그램은 OpenQASM이 표현할 수 있는 의미인가? IR 전체를 한 번 순회하며 모든 위반을 수집합니다(첫 오류에서 멈추지 않음). 그 결과는 단단한 게이트입니다: 오류가 하나라도 있으면 OpenQASM은 전혀 생성되지 않습니다 — 그래서 깨진 프로그램이 조용히 "성공한 척"하며 틀린 회로를 돌려주는 일은 결코 없습니다. 이때 검증기는 통합 심볼 테이블도 만들어요. 파라미터, 레지스터, 측정 비트, 변수, 상수, 루프 변수가 어느 스코프에 사는지 기록하고, 각 이름이 어디에서 사용되는지도 함께 모읍니다. 모든 규칙에는 안정된 코드 (QSEM001–QSEM025)가 있어 에디터가 물결선을 붙일 수 있습니다. 그중 몇 가지:

코드거부하는 것
QSEM002유저 op에 대한 Controlled Foo(OpenQASM에는 def용 ctrl @가 없음)
QSEM006시그니처와 맞지 않는 인자의 호출 — 개수, 종류(큐비트 vs 각도), 또는 레지스터 크기
QSEM007알 수 없는 게이트/연산 이름("혹시 …?" 힌트 포함)
QSEM011재귀 호출(OpenQASM def는 재귀 불가)
QSEM016레지스터 범위를 벗어난 리터럴 큐비트 인덱스
QSEM025스코프 안에서 해소되지 않는 식별자 — 알 수 없는 이름 또는 선언 전에 사용된 고전 이름
왜 변환 패스들보다 먼저 검증하나? 이후 모든 패스가 프로그램이 이미 온전하다고 가정할 수 있게 하기 때문입니다. 단형화기는 스코프에서 해소되지 않는 이름을 만나지 않고, 이미터는 잘못된 호출을 만나지 않습니다. 게이트가 모두의 앞에 서 있기에 각 변환 패스는 단순해질 수 있습니다.

6Monomorphize — 큐비트 배열 호출의 특수화

in: 검증된 HIR  ·  out: 구체적 크기의 op을 가진 HIR  ·  패스: Monomorphizer

표면 타입 Fanout(q: Qubit[])에는 배열 길이를 적지 않습니다.
단형화기(monomorphizer)는 각 호출부에서 실제 레지스터 크기를 읽어 구체적인 내부 복사본을 만들고, 파라미터에 알려진 폭을 부여한 뒤 호출이 해당 복사본을 가리키도록 다시 써요.
공통 HIR에서는 q.Count를 보존하고, target이 나중에 알려진 폭을 사용해 내려요.
예제의 호출은 reg(큐비트 3개)를 넘기므로:

Prep.Fanout(Qubit[])  +  크기 3 레지스터로의 호출  ⟶  Prep.Fanout__sz3(Qubit[3])

이제 폭이 구체적이므로 프로그램은 두 번째로 검증돼요.
인덱스 범위와 레지스터 크기 일치 검사가 비로소 대조할 값을 얻고, 이 패스 이후에는 제네릭 연산이 남지 않아요.

7Lower — 소스 모양 HIR에서 SSA/CFG MIR로

in: 검증된 specialized HIR + 의미 정보  ·  out: MirSnapshot  ·  패스: QoraMirLowering

HIR은 사용자가 작성한 프로그램 모양을 유지하므로 이름 해소, 타입 검사, 진단에 알맞아요.
그 책임을 마치면 QoraMirLowering이 실행 중심 표현을 만들면서, 고전값에는 SSA version을 붙이고 분기와 반복은 명시적인 제어 흐름 그래프로 바꿔요. 

var x: int = 1;
x = x + 1;

↓ QoraMirLowering

v0 = constant 1
v1 = add v0, 1
return

결과는 MirStage.Lowered 상태의 정확한 불변 MirSnapshot 객체예요.
이 객체는 실제로 소비한 final HIR을 LoweringSource로, MIR의 source provenance를 program-owned Origins로 보존해요.
컴파일 identity는 LoweringSource에만 있고 MIR에 다시 복사하지 않으므로, backend는 이름이나 중복 ID로 MIR의 출처를 추측할 필요가 없어요.

8MIR 분석과 내부 역연산 실체화

패스: exact MirProgram 분석 → MirAdjointMaterializer

제어 흐름, 효과, 별칭, 메모리 상태, 경로 조건, 제어 영역 분석은 자신이 설명하는 정확한 MirProgram 객체에만 묶여요.
분석 결과를 HIR에 복사하지 않으며, 새 프로그램을 가진 snapshot에 이전 프로그램의 사실을 재사용하지도 않아요.

역연산 요청도 오직 MIR에만 존재해요.
컴파일러 내부 scheduler가 정확한 MirQuantumApply 하나에 MirFunctor.Adjoint를 붙이면, MirAdjointMaterializer가 필요한 역방향 MIR callable을 합성하고 요청을 typed callable target으로 바꾼 뒤 이전 snapshot을 exact TransformationSource로 가진 새 snapshot을 발행해요.
Qora 소스와 HIR에는 Adjoint, 역연산 표식, conjugation node가 없어요. 

MirQuantumApply(Target = Prepare, Functors = [MirFunctor.Adjoint])
                         ↓ MirAdjointMaterializer
MirCallable __qora_inverse_...(reversed unitary body)
MirQuantumApply(Target = __qora_inverse_..., Functors = [])
왜 이 경계를 MIR에 두나요? 자동 uncomputation은 SSA version, CFG 경로, storage 상태, 정확한 instruction identity가 필요해요.
요청과 합성 callable을 MIR에 두면 scheduler와 materializer가 같은 근거를 공유하면서도 HIR에 컴파일러 전용 문법을 추가하거나 별도 target 경로를 만들지 않을 수 있어요.

9OpenQASM target lowering과 방출

in: materialized MIR  ·  target: MirOpenQasmTargetProgram  ·  패스: MirOpenQasmLowering → MirQasmEmitter

OpenQASM backend는 정확한 materialized MIR snapshot을 소비해요.
CFG에서 구조화된 if, while, loop exit를 복원하고, SSA 값과 phi edge를 typed target declaration과 assignment로 바꾸며, 충돌 없는 OpenQASM 이름도 이 단계에서 정해요.
결과인 MirOpenQasmTargetProgram은 target type, callable, declaration, statement와 target-local identity를 소유하고, HIR을 두 번째 권위 저장소로 들고 있지 않아요.

그다음 MirQasmEmitter가 이 target model을 직렬화해요.
source 이름을 다시 해소하거나 semantic fact를 조회하고, 역연산을 합성하거나 제어 흐름을 재구성하지 않아요.
앞으로 다른 backend가 추가되어도 HIR 파이프라인을 분기하지 않고 같은 canonical MIR을 자기 typed lowering으로 소비할 수 있어요.

이 형태는 의도된 것입니다: 엔진과의 경계 하나, 그다음 각자 IR에 한 가지 일만 하는 작은 패스들의 일직선, 그리고 그 앞에 선 검증 게이트 덕분에 이후 모든 것이 단순해질 수 있습니다. 언어 기능을 추가하는 것은 보통 한 패스를 추가하거나 확장하는 일이지 — 컴파일러를 다시 쓰는 일이 아니며 — 끝의 출력 전용 이미터는 여러분이 얻는 OpenQASM이 패스들이 만든 IR 그대로임을 뜻합니다.

이것이 향하는 곳 — 자동 언컴퓨테이션 Silq식 자동 언컴퓨테이션 — 임시 큐비트가 더 이상 필요 없어지는 지점을 찾아 그 역연산을 자동으로 주입하는 것 — 을 위한 단계 경계는 이제 MIR에 있어요.
scheduler는 exact MirProgram에 묶인 SSA/CFG 사실을 소비해 전역 cleanup 순서를 구하고, 정확한 MIR instruction에 inverse request를 주입하게 될 거예요.
MirAdjointMaterializer와 typed target 경로는 이미 이 표현을 소비해요.
다만 조건문·반복문·별칭·고전 witness 안정성·여러 ancilla 사이의 충돌은 scheduler가 해당 사례를 허용하기 전에 명시적으로 증명해야 해요.
